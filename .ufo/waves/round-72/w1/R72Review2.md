## 4. The exactly-once guard

- Sound for its purpose and fail-closed: control lines 43-47. HOOK presence via `includes` (line 43); each semantic `from` must occur exactly once else exit 2 BEFORE any mutant runs (lines 44-47); `String.replace` replaces the first occurrence only, which with count==1 is the only one, so a mutant can never silently equal the unmutated counter and can never edit an unintended occurrence. Verified on frozen bytes: HOOK 1×, all 12 `from` strings 1×.
- F4 (minor, control design): `killed := r.code === 1` (control line 71) cannot distinguish "battery found a failing case" from "battery crashed" (a node uncaught exception also exits 1; `run()` leaves the summary null). This is the only theoretical false-HOLDS channel found: a crash-kill could mask a live mutant. With the frozen class list it is unreachable — none of the 12 edits touch CHECK_IDS/--list-checks, all `to` strings are syntactically valid on frozen bytes, and the hook edit is semantics-neutral for non-forced ids. r73 control should require the battery summary JSON to parse (`j != null`, i.e. failedCases non-null) before recording a kill.
- F5 (note, symmetry): HOOK is guarded by `includes` only while semantics get count==1. On frozen bytes this is moot (1 occurrence). If a future counter duplicated the hook-shaped line, force-true would under-force (only the first site forced) → survivors → honest `holds=false` (fail-closed, never a false HOLDS). Recommend the same count==1 guard for HOOK in r73.
- `holds` requires unmutated battery exit 0 (control line 84): receipt-dependent by design — on the leg-a receipt the control would honestly report holds=false because F1's case fails there. Kill power was measured by the L1 on smoke1 only (committed receipt above); that is the only committed receipt where the unmutated battery is clean, and my per-mutant evidence is consistent with it.
