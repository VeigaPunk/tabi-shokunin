## Round 17 — declarative invocation and form mechanics

The discovery report marks iterations 1–2 defective and excludes them; its stable observations are drawn from later runs (`.ufo/waves/round-17/w1/C2ProbeDeclarative.md:18-20`).

- With autosubmit, CDP input `{q, color:"green", agree:true}` fills text/select/checkbox before the invocation response; the select becomes green, checkbox `checked:true`, and FormData reports `agree:"on"`. A trusted `SubmitEvent` has `agentInvoked:true`, `:tool-form-active` matches, and the handler's `preventDefault()` then `respondWith()` yields `Completed` with the page's result (`.ufo/waves/round-17/w1/C2ProbeDeclarative.md:25-45,57-70`). `getTools()` exposes select enum/anyOf and checkbox boolean schema; this is the only prior select/checkbox invocation and its values are valid (`:81-84`).
- Without `toolautosubmit`, invocation fills and waits; no submit/response until the page calls `requestSubmit()`. Calling `respondWith` before `preventDefault` throws `InvalidStateError`; second call after prevention succeeds. A preventDefault without respondWith becomes an `Error`; an unhandled autosubmit navigates and completes with empty-array output (`.ufo/waves/round-17/w1/C2ProbeDeclarative.md:35-50,71-80`). These are submission/response outcomes, not invalid field-value tests.
- The committed `invoke-declarative-form` case itself uses only a valid `q` string; emitted schema is object with `q` string/description Query, `required:[]`, and autosubmit annotation. Invocation returns `Completed`, and the submit listener sees a trusted agent-invoked event and returns its `respondWith` output (`corpus/evidence/round-17/webmcp-invoke/receipt.json:4269-4415`; emitted schema specifically `:4395-4415`).
- Frame probe: plain no-button/no-autosubmit declarative invocation returns a missing-submit-button error; autosubmit without a handler navigates and completes with `output:[]`; button-only form produced `toolInvoked` but no `toolResponded` or navigation in 12s and 30s runs (`.ufo/waves/round-17/w1/C2ProbeFrames.md:69-79`). None is a schema-invalid input test.

## S071 reconciliation — contradiction boundaries

S071's dossier is a Chromium 154 source read, not a browser probe. It describes the declarative call chain to `FormMCPSchema::FillData`, which has distinct unknown-parameter and invalid-`ValidateParameterData` rejection branches; it says these checks occur before values are applied (`.ufo/waves/round-18/sources/DeclarativeValidation.md:14-38`). It further limits the claim: the check is against the form-derived parameter map rather than a JSON Schema text comparison, and custom elements return true from the per-type validator (`:36-38`). Its example of unknown key `y` against a form containing `x` is a static prediction; the dossier explicitly says it was not run in a browser (`:30,36`).

**Contradiction to flag:** r17 skill/note wording that says Chromium's invoke path never validates input or only checks JSON syntax/object is overbroad when read as applying to both tool kinds (`.ufo/waves/round-17/drafts/skill2.md:103-105`; `.ufo/waves/round-17/drafts/note-c2.md:56-58`). Round-18 errata records the correction: the observed mismatch was imperative; S071 says declarative FillData rejects unknown names and invalid supported values, while required-field absence is not established (`.ufo/waves/round-18/drafts/w2-source-errata.md:160,164-168`). The r16/r17/r18 invalid-input runtime results above are imperative and therefore do not themselves contradict S071's declarative branch.

**No runtime resolution yet:** round-16 emitted `required` and `enum` schema keywords, but did not invoke those matrix tools; round-17's declarative invocation used a valid enum choice. Thus missing-required, out-of-enum, range/pattern/format, multi-select shape, and invalid checkbox values remain unobserved here. S071 does not establish required-field absence behavior, a general JSON Schema validator, or the outcome for every control type (`.ufo/waves/round-18/drafts/w2-source-errata.md:164,168`; `.ufo/waves/round-18/sources/DeclarativeValidation.md:36-38`).

## One bounded move for the C1 family seats

Keep one explicit distinction in each family's evidence record: **(1) announced schema** vs **(2) invocation outcome and post-invoke form state**. Reuse the r16 schema observations above as fixture baselines, but do not convert `required`, `enum`, `minimum`/`maximum`, `multipleOf`, or `format` in `toolsAdded` into an enforcement expectation. Pair any claimed decision with an actually observed declarative invoke status/error and field state; keep unknown-parameter and invalid-value cases separate, and label missing-required/out-of-enum results as unknown until run.
