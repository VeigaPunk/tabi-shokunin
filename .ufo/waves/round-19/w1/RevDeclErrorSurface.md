# DevTools WebMCP response/error surface (C1 depth)

## Reconstructed contract

Scope is the DevTools frontend pinned at `ChromeDevTools/devtools-frontend` commit `66df492aaa0129d090937e933dd44c5389ab24d2`, the Chromium 154 DEPS-pinned revision referenced by existing S068. This is frontend source/test evidence, not a runtime observation of a malformed declarative form invocation.

1. **Protocol values and payload fields.** Chromium 154's WebMCP PDL defines exactly three `InvocationStatus` values: `Completed`, `Canceled`, and `Error` (S041; `WebMCP.pdl:25-30`). `toolResponded` carries an invocation id and status, plus optional `output`, `errorText`, and `exception` (`:109-122`). Its contract says output is absent unless status is `Completed`; exception is described as the JavaScript-thrown-error object. The generated frontend protocol type at this DevTools commit mirrors the same three values and optional response fields (`protocol.ts:20223-20227, 20351-20372`). `Pending`/`In Progress` is not a protocol status: it is represented by a call whose `result` is still undefined.

2. **Model handoff.** `WebMCPModel.toolInvoked` creates and indexes a call by `invocationId`; `toolResponded` looks up that id and ignores an event if there is no already-known call. For a known call it converts `params.exception` into an SDK `RemoteObject`, constructs `Result(status, output, errorText, exception)`, then dispatches `TOOL_RESPONDED` (`WebMCPModel.ts:230-258`; the response lookup/construction is already covered by S068 at `:249-257`). `Result` keeps status/output/errorText and privately retains the remote exception. Accessing `symbolizedError` lazily asks `DebuggerWorkspaceBinding.createSymbolizedError(exception)`; without an exception it resolves to null (`WebMCPModel.ts:21-49`).

3. **Status rendering.** The call-list status cell maps `Error` → localized “Error”, `Canceled` → “Canceled”, `Completed` → “Completed”; its default is localized “In Progress” (`WebMCPView.ts:423-432`). The row's error/canceled classes, filter options, icon groups, and counters also use those three enum members. `undefined` result is the pending bucket (`:268-284, 335-355, 516-519, 621-635`). A status does not itself supply or display an error message.

4. **Compact row versus details.** With no call selected, the output cell renders `JSON.stringify(output)` when `output !== undefined`; otherwise it renders `errorText ?? ''` (`WebMCPView.ts:567-577`). It does not show the exception in that compact cell. The selected call's Output tab passes `output`, `errorText`, and `symbolizedError` to `PayloadWidget` (`:608-616`). In `PAYLOAD_DEFAULT_VIEW`, a defined output wins and is rendered as a read-only object tree; otherwise a string input is shown as source text, then a resolved symbolized exception is rendered through `Console.SymbolizedErrorWidget`, then a truthy `errorText` is shown in an `.error-text` div; if none are present, the payload view is empty (`:984-1045`). Thus, when both exception and `errorText` are present, the symbolized exception wins in the detail pane once available; `errorText` is the fallback. During asynchronous symbolization the widget first updates with no resolved exception, then rerenders on resolution (`:1088-1105`). An empty `errorText` is not rendered by the details view's truthiness check, while the compact row's nullish fallback preserves an empty string as empty.

5. **Declarative tools share this response path.** The frontend classifies a tool as declarative when its CDP tool has `backendNodeId` (`WebMCPModel.ts:118-125`). In the view, `isDeclarative` only participates in the tool-type filter (`WebMCPView.ts:288-299`); the result/status/output rendering is common to declarative and imperative calls. There is no separate “fill error” renderer or declarative-specific status enum in this view.

### Divergence / confidence

- **High confidence** in the frontend's mapping and precedence above: it follows the pinned model, view, generated protocol, and checked-in test code. The existing S068 correlation anchor covers `WebMCPView.ts:942-952` and `WebMCPModel.ts:249-257`; the response-rendering ranges and `Result` adapter are distinct line anchors.
- **Not established here:** what Chromium 154 actually emits in `toolResponded` for a particular invalid declarative form input. The frontend accepts optional `errorText` and `exception` independently and does not infer either from `status`. Do not treat the test's “Permission denied” fixture as browser output. Existing S042 is separate Blink source-level evidence for a JavaScript throw/reject path and cannot be generalized to every declarative fill/validation failure. A runtime receipt or the exact Blink fill path is needed to claim the observed payload for a specific case.
- No browser, CDP runtime, build, or test suite was run for this assignment. Tests mentioned above are source fixtures/assertions only. No tool was installed or updated.
