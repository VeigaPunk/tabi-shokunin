# C1 case-contract review

## Verdict

The current contract is not yet deterministic enough to hand unchanged to 15 independent family seats. The case shape is small, but its no-response sentinel, field/schema comparators, fixture serialization, case discovery, and runtime identity need shared exact rules. The 14 clarifications below are scoped to the case contract and its harness interface; they do not claim any round-19 runtime result.

## Exact clarifications

1. **P1 — Separate no response from invoke failure.** Define `expect.status` as the exact, case-sensitive `toolResponded.status` from the event matching the `invocationId` returned by `WebMCP.invokeTool`. Permit `no-response` only when the invoke command succeeded with a non-empty `invocationId` and no matching event arrived during the complete 8,000 ms window measured from the CDP command response; preferably name this bounded result `no-response-within-8000ms`. A CDP protocol error or missing `invocationId` is a separate invoke outcome (`invokeError` expectation) or `could_not_evaluate`, never `no-response`. Record the invoke reply/error and matched event params in `observed`. Evidence: `PLAN.md:98-100,116-119`; the prior harness keeps invoke errors separate from invocation IDs and correlates responses by ID (`scripts/webmcp-invoke-round18.mjs:1279-1297`; same pattern in round 17 at `scripts/webmcp-invoke-round17.mjs:1260-1272`).

2. **P1 — Pin error-text matching.** State that a non-null `errorTextIncludes` must be a non-empty, case-sensitive substring of the matched event's string-valued `errorText`; a non-string `errorText` fails the assertion. Define `null` as “do not assert an error-text substring,” not as a claim that the property is absent or JSON null. If absence/empty text must be asserted, add a separate exact-value/presence expectation. Evidence: `PLAN.md:99`.

3. **P1 — Add an output expectation.** Add optional `expect.output` for the matched `toolResponded.output`, with an explicit way to distinguish an absent property from an output of JSON `null`; compare JSON values structurally. Otherwise `pass:true` can ignore an incorrect successful result from `respondWith` while status, form state, and schema all match. Evidence: the fixture promises a concrete `respondWith` result (`PLAN.md:105-108`), but the expectation shape omits output (`PLAN.md:98-101`).

4. **P1 — Replace dotted schema paths with a defined path grammar.** Use JSON Pointer (RFC 6901), so an array branch is unambiguous, e.g. `/anyOf/0/properties/q/type`; define `""` as the root, array indices as canonical decimal indices, and `~0`/`~1` escaping. A missing path must fail rather than compare as `undefined`. Compare actual and expected values by strict JSON structure: object key order ignored, array order retained, and no type coercion. Evidence: `PLAN.md:100-101`.

5. **P1 — Distinguish skip from JSON null.** Define top-level `expect.fields: null` and `expect.schema: null` as “skip this comparator.” Within a schema path map, an expected JSON `null` means the path must exist and its value must be null; missing and null are different. Apply the same explicit presence rule to `expect.output`. Evidence: `PLAN.md:100-101`.

6. **P1 — Define typed form-state snapshots.** Replace `fields` as a name-to-value map with an ordered array of named-control snapshots, one per `form.elements` entry in DOM order, so duplicate names survive. Specify a fixed record such as `{name, tagName, type, value, checked, selectedValues}`: `value` is the DOM value for ordinary controls and checkbox/radio controls; `checked` is the actual boolean for checkbox/radio; `selectedValues` is the ordered selected-value array for `<select multiple>`; non-applicable slots are null. Include every control with a `name` attribute, including unchecked controls; do not collapse multiple controls into one entry. This makes checkbox state distinct from an omitted FormData entry and represents multi-select values without loss. Evidence: `PLAN.md:100,106,116`.

7. **P1 — Preserve duplicate form-data entries in the fixture response.** The specified `Object.fromEntries(new FormData(...))` object shape loses repeated keys (including same-name checkboxes and `<select multiple>`). Specify a deterministic grouped representation such as `{name: [values...]}`, with values kept in `FormData` entry order and arrays used even for a single value; or state that the fixture response is not evidence for field comparison and use only the typed DOM snapshot from item 6. Evidence: `PLAN.md:105-108`.

8. **P1 — Make tool registration observation race-free and bounded.** Require the CDP event recorder to be active before `WebMCP.enable` is sent, then inspect recorded `toolsAdded` events so an event arriving before the enable command response is not missed. Define a bounded registration wait (recommend 8,000 ms from the enable response) and require exactly one matching tool entry by exact `tool` name. No match, multiple matches, or absent/malformed `inputSchema` when a schema assertion is requested is `could_not_evaluate`, not a passing null. Evidence: `PLAN.md:115-116`; the prior harness records events and selects tools by exact name (`scripts/webmcp-invoke-round18.mjs:1228-1264`).

9. **P1 — Define observation time and submission counting.** Define `submitCount` as `window.__obs.calls.length` for the selected form, sampled once after the matching `toolResponded` event or after the full no-response window. For a no-response case, treat only events received within that window as observed absence; do not claim permanent absence. Compare counts strictly (`>1` is a mismatch), and treat an inaccessible page/form at snapshot time as unobservable/exit 2 rather than a null pass. Evidence: `PLAN.md:100,106,116-119`.

10. **P2 — Fix case discovery and ordering.** Specify `--cases DIR` as the non-recursive directory of `*.json` case files; use the default `corpus/evidence/round-19/validation/cases`. Process filenames in bytewise lexical order and preserve each file's `cases` array order. Require unique case IDs across all loaded files and reject duplicates before invoking anything; never overwrite or merge records by ID. Evidence: `PLAN.md:92-103,117-119`.

11. **P2 — Specify family and fixture path identity.** Require each filename to be exactly `<family>.json`, `family` to be a canonical lowercase slug, and `fixture` to be the basename `<family>.html`. Define the fixture root as the sibling `../fixtures` directory of the selected cases directory, and reject traversal, absolute paths, symlinks/escape, missing fixtures, and external URLs. This removes ambiguity in the current `--cases DIR` option, which does not state how to locate fixtures. Evidence: `PLAN.md:92-94,96-103,105,117`.

12. **P2 — Define corpus/schema error behavior.** State that malformed JSON, unsupported case schema/version, duplicate IDs, invalid case values, missing fixtures, or non-unique form/tool registration are harness-evaluation failures (exit 2), while a well-formed case whose observed values differ from its expectation is an assertion failure (exit 1). No malformed or skipped case may silently disappear from the receipt; receipt `pass` is computed by the harness, not supplied by a case file. Evidence: `PLAN.md:96-103,117-119`.

13. **P2 — Assert observed runtime identity, not just configured paths.** Keep one Chromium process/runtime per harness invocation with a fresh isolated context and page per case, and assert the observed browser version is Chromium 154.0.8037.97, Playwright is 1.64.0, and Node is 24.21.0 before any case can pass. Record the resolved executable identity as well as the configured launch path. Round 18 records the observed browser version but explicitly does not assert it, so copying its recorder unchanged would not satisfy C1's pinned identity. Evidence: `PLAN.md:111-119`; `scripts/webmcp-invoke-round18.mjs:2872-2891`.

14. **P2 — Bind each source locator to the same pinned source.** Define `lines` as inclusive, require `file`, `lines`, and `url` to identify the same Chromium 154.0.8037.97-tag file/range, and add the matching `S###` source ID (and decoded-body SHA-256, or an equivalent authenticated source-record reference). Reject a URL/path/tag mismatch instead of accepting a syntactically present anchor. Evidence: `PLAN.md:102-103`; the C1 claim's source-row condition is in `PLAN.md:22-28`.
