## 1. What the spec fixes (S164, located; receipt `sources/s164-fetch-receipt.json`)

- **pointerType is a defined value set, not free text.** The definition says "Indicates the device type that caused the event (such as mouse, pen, touch)." (§3.1, raw 1699, 13 words), and the normative table maps Mouse to `mouse`, Pen / stylus to `pen`, Touch contact to `touch` (raw 1705–1707). "If the device type cannot be detected by the user agent, then the value MUST be an empty string." (raw 1710, 19 words). The IDL declaration is `readonly attribute DOMString pointerType;` (raw 1623). The row's tier A scope stops here: the point is the three-value set the counter checks against.
- **pointerId is an implementation-specific identity.** "A unique identifier for the pointer causing the event." (§3.1, raw 1632, 9 words). "user agents MAY reserve a generic pointerId value of 0 or 1 for the primary mouse pointer." (same line, 17 words). "The pointerId value of -1 MUST be reserved and used to indicate events that were generated by something other than a pointing device." (same line). The IDL declaration is `readonly attribute long pointerId;` (raw 1613). The spec then says the selection algorithm is implementation specific and that authors must not read meaning into the value beyond uniqueness among active pointers (raw 1635) — which is why the counter requires a finite non-negative number and stable identity across one press, not a particular number.
- **pointerdown is the buttons-pressed event.** §3.3.3 (raw 2226) gives `Type` `pointerdown`, `Interface` `PointerEvent`, `Bubbles` Yes, `Cancelable` Yes, `Composed` Yes (raw 2232–2249), and "The user agent MUST fire a pointer event named pointerdown when a pointer enters the active buttons state." (raw 2261, 18 words).
- **isTrusted is NOT defined by S164 (finding).** The served bytes mention `isTrusted` three times (raw 3822, 3937, 3992) — coalesced-event and predicted-event re-dispatch rules and the inherited-property rule — but none is a definition; `sources/s164-quotes.json` records `definesIt: false` and all three hrefs point at `https://dom.spec.whatwg.org/#dom-event-istrusted`. The definition site is the DOM Standard's `Event.isTrusted`; no registered lane row scopes it (S163 is scoped to `cancelable`). The counter's `isTrusted === true` check is therefore a page-side browser-behaviour witness, not a fact admitted from S164.
- **Grounding boundary.** The Pointer Events spec defines the page-side interface. It does not define CDP. The `dispatchMouseEvent` shape comes from the pinned CDP protocol bytes (S153's file): `pointerType` is a string parameter with default `"mouse"` (raw 14558), `button` an enum defaulting to `none`, and `buttons` the pressed-button bit field (Left=1, Right=2, Middle=4). `sha256sum` on the round-61 staged copy `sources/s153-browser-protocol.json` gives `d6737c31f268ed74e65dde393006dd9c590a713febd2361d734722eb059f31e7`, byte-identical to the S153 anchor (1,423,170 B). Scope notes: (i) the scout's S153 quote set, `sources/s153-quotes.json`, quotes the command at raw 14458 but not the `pointerType` parameter — this note cites it from the staged bytes and flags the quote-set gap for the L1; (ii) S153's registered `scope` cell names Page.captureScreenshot and the `/json/new` PUT, so the dispatchMouseEvent parameter is outside the registered scope cell; the round-61 re-open and mismatch are recorded in the lesson Gate and Limits (no scope-cell edit is made, per R1).

## 2. What the page records (measured model)

`window.__ptrlog` is the page's pointer-only log; `window.__mouselog` is the mouse log; both share a page-side `window.__seq` counter, and every entry carries a globally unique monotonic `seq` (plus `ts`, `button`, `buttons`, and for pointer entries `pointerType`, `pointerId`, `isTrusted`). The frozen C2 predicate names the pointer fields the page must witness: `type` in {`pointermove`, `pointerdown`, `pointerup`}, `pointerType` `"mouse"`, a numeric `pointerId`, `isTrusted` true, and numeric `button`/`buttons`. The receipt copies both arrays as `ptrlog` and `mouselog`, reads `focus` immediately after the press, and (for the typing leg) `nonce` + `plainTrace.entries`.

**Cross-instrument contract (observed live, reconciled pre-freeze).** At 23:07 UTC the counter (`checkPointerDomain`, current line 1731) required pointer-only `ptrlog`, mouse-only `mouselog`, and a monotonic `seq` on every entry, with `pointerdown.seq < mousedown.seq < pointerup.seq < mouseup.seq`; the runner bytes at 23:06 wrote one combined `__ptrlog` with `ts` and no `mouselog`, so the live receipt would have failed `pointer-log-wrong` and `pointer-order-wrong`. ## 3. The focus contract

The pointer press, not a scripted `.focus()` call, moves focus: after `mousePressed` the receipt's `focus` field equals `"field"` (`document.activeElement.id` read immediately after the press). The second input `#field2` is the never-focused control. Consequence: the subsequent key dispatch lands in `#field` because the pointer press focused it; the counter refuses a receipt whose `focus` is anything else (`pointer-focus-wrong`). Evidence: `focus` in the committed receipt; the runner's own negative witnesses `journey.form.field2Focused` (expected false) and `journey.form.field2Value` (expected empty) in `scripts/chrome-cdp-loopback-round61.mjs` (press then read).

## 4. The nonce-typed field trace

After the focus, the driver types the run's nonce into `#field` with `Input.dispatchKeyEvent` keyDown/keyUp (the r52 pattern) and reads the field value back after EVERY keystroke. The receipt carries `nonce` and `plainTrace.entries`, where entry `i` is `{i, char: nonce[i], valueAfter: nonce.slice(0, i + 1)}`. The counter re-derives the whole trace from `nonce` and refuses a receipt whose trace is short, reordered, or carries a value that is not the nonce prefix (`pointer-nonce-wrong`). This binds the receipt to the run: a forged receipt with a different typed string cannot re-derive.

Measured: nonce `<L1-fills: value>`, `plainTrace.entries` length `<L1-fills: == nonce length>`, field value readback after the final key `<L1-fills>`. Evidence: `nonce` and `plainTrace.entries` in the committed receipt; counter `pointer-nonce-wrong`.

## Scope and limits (stated, not smoothed)

- **One surface, one pointer.** Linux host, `/usr/bin/chromium 155.0.8059.84`, loopback fixture, throwaway HOME/XDG, one mouse pointer. No real site, no touch contact, no pen/stylus, no multi-pointer or multi-button chords, no IME, no pointer capture, no coalesced or predicted events. S164's full value set is named (mouse, pen, touch); only `mouse` is measured.
- **pointerId is not portable.** S164 makes the selection algorithm implementation specific; the observed number (L1-fills) is a witness of this run, not a rule for other builds or runs. The stable property the note relies on is identity across one press/release.
- **isTrusted has no registered definition site.** S164 references but does not define it; S163 is scoped to `cancelable`; this note does not open a DOM Standard row for `isTrusted`. The `isTrusted: true` witness is measured page-side and the counter enforces presence and boolean true.
- **S153 scope mismatch (disclosed).** The dispatchMouseEvent `pointerType` parameter lives in the pinned CDP bytes whose registered scope names Page.captureScreenshot and `/json/new`; this note reads the parameter but does not widen S153's scope cell. The round-61 lesson `## Gate` records the re-open and the mismatch.
- **The receipt is a schema superset.** `tabi-chrome-cdp-r61` adds `ptrlog`, `mouselog`, the page-side `seq` stamps, `focus` and a complete `plainTrace`; the r59/60 checks are carried unchanged on r59-shape receipts. A byte-perfect replica of the live receipt passes by construction (the carried disclosure class), and only the frozen forgery set F and named mutants were measured.
- **No driver-side trust claim.** The note does not claim the page can distinguish a CDP-dispatched event from a physical one beyond `isTrusted`; it records what this surface reports.
