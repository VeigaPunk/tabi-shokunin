## High — The written rules admit receipts not derived from the row source

The counter criteria in `.ufo/waves/round-18/PLAN.md:69-77` require `rowUrl` to occur in the row's `source` cell, but do not require the recorded fetch `url` to equal that URL or an approved transformation of it. They check that a quote occurs in the excerpt and that the excerpt hash matches its own bytes; they do not bind either to the bytes fetched from the row source. `recheck-fetch.mjs:86-100` accepts arbitrary `--url` and reads arbitrary `--body`; `:103-109` builds the excerpt from whichever bytes were supplied; `:110-135` records self-reported command/quote-source/anchor fields and hashes those bytes, but does not authenticate them.

Two probes produced receipts that satisfy the enumerated fields, assuming the current producer file is committed unchanged at REV:

1. **HTTP URL override:** S016's registry URL is `https://playwright.dev/docs/test-assertions` (`corpus/SOURCES.md:30`). I passed that as `--row-url`, but passed `https://playwright.dev/docs/test-retries` as `--url`, with the 13-word quote “Test retries are a way to automatically re-run a test when it fails.” The tool returned `RECHECK row=S016 http=200 bytes=99073 sha256=cf48ff4db0a305f9c1a8a829b60c295041e22daa0e018c4286ae182832ffbdfa quoteFound=true verdict=held`. The JSON recorded the mismatched URLs, `quoteWords: 13`, `quoteFound: true`, a matching excerpt hash `0c56fc144247fc2d40b4a7fb2549b54561b47fde15a70ad5b8d803179a25c5aa`, and `producerSha256: f2ba0033323a3806f62697d6cff52c1916d6c4d4ffd44a6fa9760d63e6eaa360`. The fetched page was 200; the quote is from `test-retries`, not S016's `test-assertions`. No listed C1 rule rejects the URL mismatch.

2. **Forged `--body` for the local row:** S029's source cell is the non-HTTP repo path `corpus/evidence/round-13/aria/receipt.json` (`corpus/SOURCES.md:43`), so its receipt is not subject to the HTTP-200 condition. The receipt's `rowUrl` exactly matches the S029 source path; `quoteWords` is 11; `excerptSha256` is the same 64-hex digest because the generated excerpt is the supplied quote; `quoteFound` is true; `fetchedAt` is 2026-10-20; and the producer hash matches the current tool file. The body path bypassed any read of the S029 source.

The plan allows `--body` for non-HTTP sources (`recheck-fetch.mjs:9`) but neither restricts its path to the source blob nor asks the counter to hash the blob at REV. Also, the `--quote` check has only a maximum of 25 words and no minimum (`:84-85`); `quoteSource` and `anchorObserved` are not validated (`:124`, `:129`). An excerpt can be invented or copied from an old lesson, hashed, and made internally consistent. `producerSha256` pins the producer code, not that the producer was run on the source URL or that the receipt/excerpt was not authored afterward.

**Concrete counter checks:**

- Resolve a canonical fetch target from the SOURCES row and a small, explicit host-specific transformation table; reject arbitrary `url` overrides. If an override is needed, require it to match the derived target exactly. `--live` must fetch that canonical target, not the receipt's untrusted `url`.
- For HTTP rows, have the counter independently fetch the canonical target, require an acceptable status/content type, and recompute bytes, hash, decode, quote occurrence/offset, and excerpt from that same response. Compare receipt fields and excerpt bytes to the recomputed values; count only a quote found in that live response. A same-origin or redirect destination must not silently substitute for the registry source.
- For non-HTTP rows, read the exact path from the REV tree (e.g. `git show REV:<row path>`) and recompute the digest/quote/excerpt from those bytes. Do not accept a caller-provided body as evidence of a committed local source.
- Validate `quoteSource`/anchor against a locator in the authenticated decoded source, and set a meaningful minimum quote length (e.g. 8 words, in addition to the 25-word cap). Require the excerpt to equal the producer's defined window around the recomputed offset, not merely contain the quote.

## Medium — One `html-text`/normalizer path is not adequate for every listed source format

`decodeBody('html-text')` is a regex tag stripper with a small entity map (`recheck-fetch.mjs:19-33`); `normalize()` only folds NFC, selected typographic punctuation/NBSP, and whitespace (`:47-52`). It does not select page main content, parse structured formats, or handle source-language markup. The named-entity fallback leaves unlisted HTML5 entities unchanged (`:32`). The current CLI also does not retain response content type: curl records only `%{http_code}` (`:95-98`).

Required three real-page probes, fetched 2026-10-20 using the tool's curl options and then run through `--normalize-only --decode html-text`:

- `developer.chrome.com/blog/remote-debugging-port`: curl `200 text/html; charset=utf-8`, 17,157 bytes; query `Chrome 136` → `found:true`, offset 3056, normalized length 5,104.
- `playwright.dev/docs/test-retries`: curl `200 text/html; charset=utf-8`, 10,801 bytes; query `flaky` → `found:true`, offset 1,189, normalized length 7,513.
- `www.w3.org/TR/webdriver-bidi/`: curl `200 text/html; charset=utf-8`, 396,118 bytes; query `Working Draft` → `found:true`, offset 34, normalized length 655,033. This proves text is extracted, but also that a generic match can be satisfied at the document header rather than the anchored normative passage; the extractor searches the whole response.

Host-specific observations:

- **GitHub blob HTML:** the pinned WebMCP `index.bs` page returned `200 text/html`, 96,827 bytes. `--normalize-only --decode html-text` did not find S043's full quote (“Despite the name of this API … browser agent.”; `corpus/lessons/round-17.md:55`). That lesson records the source's `Web*MCP*` and `[=browser agent=]` markup versus the rendered wording. The generic HTML stripper does not interpret that source markup, and this fetched blob response did not contain the full normalized quote. Use an explicitly selected raw/rendered representation and a matching source-aware quote/decoder.
- **Gitiles `?format=TEXT` base64:** the Chromium 154 source returned `200 text/plain`, 18,512 bytes. Base64 decoding succeeded, but the exact S042 quote in `corpus/lessons/round-17.md:54` was not found (`found:false`, normalized length 43,413). A shorter `argument string` probe showed the decoded text has `//` comment prefixes between the sentence fragments. The lesson explicitly says the quote excludes those prefixes and was found after removing them. Thus the current base64 decoder works, but this row's quoted form does not match the current normalizer.
- **MDN and Selenium:** the MDN module page returned 200 and `WebDriver BiDi` was found at offset 0 (normalized length 8,660); the Selenium page returned 200 and `WebSocket` was found at offset 2,667 (normalized length 6,412). These establish basic server-rendered text extraction only; the MDN query matched the page heading, not a substantive row locator.
- **Stack Exchange API:** a real answer API response was `200 application/json`, 435 bytes, containing answer 74926242 with nested HTML in `body`. `html-text` did find the answer's code quote `await new Promise(resolve => setTimeout(resolve, 5000));`, but its normalized window still contains the surrounding JSON fields and answer metadata. The tool has no JSON decode/answer-selection step, so it cannot establish that a match came from the intended `answer_id` and `body` rather than another JSON field/item. Parse JSON, select the expected answer id, then parse/normalize that body's HTML.
- **IEEE/ACM DOI endpoints:** the current S022 IEEE URL (`corpus/SOURCES.md:36`) returned `202 text/html`, zero bytes on this fetch; the representative ACM DOI URL `https://dl.acm.org/doi/10.1145/3695989` returned `403 text/html`, 3,087 bytes. Normalization found no test quote in either response. S022 therefore cannot meet the plan's required HTTP 200/quote-found rule with this fetch route. S019 itself points to the KNU institutional page, not an ACM URL (`corpus/SOURCES.md:33`); the ACM response is a representative endpoint probe, not a current SOURCES row. An unreachable row cannot count under the stated 51-row target unless it is reopened through an approved source or the target/eligibility contract changes.

**Concrete decoder/normalizer checks:** select the expected document body (not the whole page), use an HTML5 parser/entity table, and record/validate content type and a row-specific decode mode. Add explicit GitHub raw/rendered and Gitiles code handling; do not globally delete comment syntax from arbitrary code, but either quote the literal source including comment markers or use a precise line-aware rule. Add Stack Exchange JSON parsing that selects the recorded answer id before HTML extraction. Treat blocked DOI responses as unreachable rather than as usable page text; resolve the source/eligibility gap explicitly.
