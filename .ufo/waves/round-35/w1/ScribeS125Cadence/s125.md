## 8. Limits

- **`--stable 156.0.8078.47` is taken from the receipt's own trigger** (S108, Chromium Dash record
  fetched 2026-10-26T04:12:21Z), not re-derived here — Chromium Dash is outside this seat's allowed
  host list. If Stable has moved, the receipt needs a new `trigger` row (S108), not an edit to the
  S125 entry; the gate would then compare against a newer tag automatically.
- **`f6` independence is name-based**, as the gate's own header says. I am a different process and time
  from `ScribeRoutedDefects`, but a different string would also pass. C1 shows the check is not vacuous.
- **The receipt entry's `fetched_by` is a prior round's seat**, on purpose: the 156 bytes were first
  fetched by `ScribeRoutedDefects` at 18:25:11Z (round-33 draft), so crediting my seat there would
  destroy the independence `f6` tests. My own fetch is the refetch record.
- **Range `378` cannot discriminate** — the normalised line `if (session->web_socket_url) {` occurs
  five times in the 156 file. The other five ranges pin the location; a receipt that sampled only
  `378` would prove nothing.
- **Anchor line numbers are 154-scoped and correct as written**; a reader re-deriving at 156 must apply
  `+4/+11/+11`. That drift is exactly what `f4-ranges` makes loud.
- **Only `session_commands.cc` is in the receipt.** `capabilities.cc` was fetched at both tags and is
  byte-identical, but adding it as a second receipt file (ranges `[1362,1362] [1375,1376]`, four more
  54,458-byte blobs) is a design change beyond this routed defect and was not made; if the L1 wants the
  parse covered by the tripwire, that is a separate, verifiable addition.
- **A 503's sha is recorded as a metric only**, per QUALITY 93; neither 503 body was retained (the same
  file path was overwritten by the successful retry), so their size and digest are the whole record.
- **The comparison is content, not behaviour**: identical source at two tags does not prove the shipped
  ChromeDriver binaries behave identically.
