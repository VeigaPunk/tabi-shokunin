=== F1 (blocking) toMatchAriaSnapshot cannot run outside the Playwright test runner ===
Evidence: lib/matchers/expect.js:13041-13043:
  const testInfo = expectConfig().testInfo;
  if (!testInfo) throw new Error(`${matcherName}() must be called during the test`);
This check happens before the string/object branch, so even the inline-string form throws in a plain `node` script.
Consequence: a `scripts/aria-loopback-round13.mjs` run as `node ...` cannot call expect(locator).toMatchAriaSnapshot at all.
Required fix (author-side, choose one before writing):
  (a) make the file a Playwright test file and run it with `npx playwright test -c <config> <file>`, or
  (b) do not use toMatchAriaSnapshot; that would violate the acceptance rule "never own substitute matching".
Choose (a). Invocation must be stated explicitly in the report.
Pitfall under (a): default testMatch in Playwright is spec/test patterns [inference, not read in the installed package]. A file named `aria-loopback-round13.mjs` will then report "no tests found" unless the config sets testMatch to that path. Ship the config (new file; it is outside the stated write set, so the parent must approve it or it must be inlined by the parent).

=== F4 (high) false green: default updateSnapshots and the `{name}` template form ===
- lib/matchers/expect.js:13054-13061, 13066-13068, 13118-13123: when the template is an object {name} and the file is missing, with updateSnapshots 'missing' (default outside CI [inference]), the matcher WRITES the actual snapshot and returns pass:true with a console log.
- Consequence: "exact committed templates" can silently pass against a just-written file.
- Required: use inline string templates (the string branch at 13050-13052 does not read or write files), OR set updateSnapshots: 'none' in the config. Do both if any file form is used. Do not rely on CI detection.
- Also: a string template that is empty makes isMissingBaseline true and fails (kImpossibleAriaMatch). Good as a fail-closed, but do not count it as a template case.

=== F5 (high) global children default: do not set toMatchAriaSnapshot.children in config ===
- lib/matchers/expect.js:13071-13074: if expectConfig().toMatchAriaSnapshot.children is set, the matcher prepends `- /children: <mode>` to any template that lacks `/children:`. Setting it would change the "default contain" case silently. Leave it unset.

=== F6 (high) `.not` assertions are vacuous when the locator matches nothing ===
- A negative `expect(locator).not.toMatchAriaSnapshot(...)` passes if the element is absent, if the locator resolves to nothing, or if the template misses for any reason.
- Required: precede each negative with `await expect(locator).toHaveCount(1)` and use a short explicit timeout (e.g. {timeout: 1000}); otherwise the negative waits the full default expect timeout (5000 ms) per case.
- For "wrong checked state rejects": the positive check must be on the same node; the negative must be the same template against the wrong state, with count asserted first.

=== F7 (medium) checked serialization is one-directional ===
- coreBundle.js:750-753: a true checkbox emits ` [checked]`; mixed emits ` [checked=mixed]`; an unchecked checkbox emits NOTHING (no [checked=false]).
- Consequence: the template `- checkbox "Agree" [checked]` fails on the unchecked box (expected: reject). A template `- checkbox "Agree" [checked=false]` never matches any state and is not a valid negative control.
- Partial matching: a template omitting [checked] passes regardless of state (corpus note §4; docs). The "wrong checked state rejects" case must include [checked] in the template.

=== F8 (medium) children-mode semantics: exact expected results ===
Parser (coreBundle.js:169-177, 242): `- /children: equal` is a key inside a node's child sequence; it sets containerMode on the node that contains it.
Expected results for the planned "contain accepts extra sibling / equal rejects same tree" case:
  Fixture tree: <ul aria-label="Items"> with <li>First</li><li>Second</li><li>Third</li></ul>
  Template A (default contain, passes):
    - list "Items":
      - listitem: First
      - listitem: Second
    Expected: PASS (extra sibling Third allowed; order preserved).
  Template B (equal on the list node, rejects the same tree when the template lists only two items):
    - list "Items":
      - /children: equal
      - listitem: First
      - listitem: Second
    Expected: FAIL (direct children must be exact; Third is extra).
  Template C (equal, all three; passes): expected PASS.
Pitfall: place `/children: equal` on the list node, NOT at top level. A top-level `- /children: equal` sets containerMode on the fragment; because the fragment is then not unwrapped (coreBundle.js:242), the comparison runs against the whole locator subtree, which is a different claim.
Pitfall: names and states omitted from a node stay unconstrained even under equal (corpus note §4 [inference], consistent with docs). Template B does not prove the listitem labels are exact unless names are included (they are, in A/B/C above).
Pitfall: whitespace inside names is normalized; names are case-sensitive in templates (docs/corpus note); the fixture text must match the template case exactly.

=== F9 (medium) Locator API pitfalls for the planned cases ===
- getByRole name and getByLabel text are case-insensitive SUBSTRING matches by default (types.d.ts:3228, 3276-3278). Use {exact: true} whenever the case asserts uniqueness.
  Duplicate-role fixture: buttons "Save" and "Save draft". Bare getByRole('button', {name: 'Save'}) resolves to 2 elements (substring). With {exact:true} it resolves to 1. The "strictness fails without first()" expected result must come from the substring collision and be asserted, and the exact-true variant should be the passing control.
- Strictness error text (coreBundle.js:20944, strictModeViolationError): "strict mode violation: <locator as code> resolved to N elements:" followed by element lines and possibly "...". Assert with /strict mode violation/ and the match count (N), not the full text (element lines are environment-shaped).
- Inference: strict violation is raised immediately on a multi-match for an action, not retried until timeout. Confirm the elapsed time in the run instead of assuming; a wait equal to the action timeout would indicate retry.
- Locators are queries re-resolved on each use (corpus note §3). The "locator re-resolves replaced node" case: capture a data-gen attribute on the node before and after `replaceWith`, then assert the locator's action or ariaSnapshot reports the new data-gen. Do NOT use elementHandle(), which pins the node and makes the case vacuous.
- ariaSnapshot(): do not use mode:"ai" (adds [ref=eN], changes digests and is a different producer); do not use boxes:true (layout-dependent). Default mode only (types.d.ts:2101-2130, 14608-14690). ariaSnapshotJSON exists in 1.64 but is not the YAML the spec asks for.
- Locator.ariaSnapshot default wait behavior: the ai-mode doc says it "does not wait", implying default mode waits [inference]. For the before/after capture, include an explicit precondition assertion (toHaveCount(1)) so the capture is not racing.
- label fill: getByLabel substring default applies; a label such as "Name" also matches "Full name" if present. Keep fixture labels unambiguous or use exact:true.

=== F10 (medium) expected-failure handling must not swallow ===

- Pattern for toMatchAriaSnapshot negatives: see F6 (count precondition + short timeout). Do not wrap in try/catch that returns true.
- Each expected failure must emit a stable finding ID and the observed message (or the matcher's received diff) into the receipt; a caught error without the message is a swallowed finding.
