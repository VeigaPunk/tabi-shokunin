## Findings

**Must-fix: none.** Every MUST-level defect below is either a declared limit or a declared driver-pin fact, and none falsifies a leg statement.

**Should-fix**
1. **Exit-3 now launders more than declared (counter L235-237, L271-274).** `failures` check L234 fires for any launch-failed leg (`l.error !== null` → `errLegs`, `failures.length===0` fails), generating a `failures` finding. But `LAW_EXEMPT = {driver-exit, failures}` means a partial-launch run with ONLY those findings goes to `setup`, not `findings` — intended. However legit `driver-exit` is also exempt. Concretely: a driver exiting 3 on a LAW leg that ALSO mis-labels it `chromium never came up` skips per-leg checks entirely (L235-237), and the `failures` finding it inevitably produces is exempted by design. This is exactly the declared-limit-8 laundering caveat ("a driver that labelled a law-failing leg that way would launder it"); the counter cannot see it (limit 8), so it is a driver-pin fact, not a counter bug. Two subtler spots the limit text does not quite name:
   - `launchFailed` is computed from ANY leg with `typeof l.error === 'string' && startsWith` — including legs that ALSO carry a law outcome, masking real leg data (outcome/files/events/reads are skipped, not merged). The driver (pinned) only throws that prefix on client-launch-throw / DevTools-never-answered (L281, L287), so on the pinned bytes this is unreachable — K-partial exercises exactly this branch, K-launchonly the all-failed branch.
   - With `partialLaunch`, receipt-level findings OTHER than `driver-exit`/`failures` (e.g. `child-files`) correctly force `findings` (rc 1), and `LAW_EXEMPT` protects legitimate launch failures from being counted as law. Verified by live-killers' expected verdicts (K-partial: frozen rc 1 `child-files`; K-launchonly: rc 2 `setup`) and by my `launchstr` hand-mutation (receipt mode: `launchFailed=[]`, rc 1 `failures` — the skip does not trigger outside --live/exit-3, as designed).
2. **Events can include read side-effects? No — but the 400 ms settle is the whole ballgame, and ordering is asymmetric.** Reads run AFTER files+events are snapshotted (L322-340), and `arrayBuffer()`/`FileReader` do not fire `input`/`change` on file inputs (they only read), so a read cannot pollute `leg.events`. Any event fired by the upload call itself lands within the 400 ms window; trusted vs synthetic is read from `isTrusted`, unaffected by timing. Real weakness: the 400 ms is wall-clock, not event-loop quiescence — under host load a late CDP-dispatched event could be missed (false events-missing finding) or, worse, attributed to the leg while it belongs to a previous chromium. The driver mitigates with one-browser-per-leg + port-release wait (L349-350) and fresh profiles, so cross-leg bleed is structurally implausible. Nit: `digest` failure in the SHA-256 hex step (WebCrypto requires secure context; `http://localhost` IS a secure context per spec — confirmed reasoning: localhost is potentially trustworthy, so `crypto.subtle` is available in the child frame; the probe/control receipts corroborate by getting ok reads) — but the code has no fallback; a future non-local child origin would turn every read into `['err','TypeError',...]` and the counter would report `child-reads`, i.e. mutable-leg-false, not `setup`. Not a defect on this host; the claim is localhost-only.
3. **TMPDIR placement correct; sweep correct; one-sided.** `process.env.TMPDIR = tmpDir` runs before `await import(puppeteer-core/playwright-core)` (driver L120-161), so `playwright-core`'s artifacts folder is under scratch — the r98 D2 fix. Counter `--live` puts TMPDIR under `<counter scratch>/driver/t` (L151-152) and checks `tmpdir-bound`. The `/proc` sweep matches `--user-data-dir=<scratch>/` (driver L178-186; counter L157-164) — covers client-launched chromium, which inherits the driver profile dir. Connect-mode chromium (`spawn(... detached:true)`, liveGroups) is killed via `-pid` group kill + sweep. Port release: driver freePorts all three before starting and waits after each leg (L172, L350); counter runs the sweep after close (L179-180). SIGINT/SIGTERM/SIGHUP handlers exist in both (counter L174, driver L188) with `orphansSwept` recorded. No leak beyond the declared `orphansSwept` counter.
4. **Receipt-binding is intentionally loose, not a hole.** `generatedAt`, extra fields, `chromium` substring, `ports-bound`/`missing-bound`/`tmpdir-bound` extras are NOT in the frozen predicate, so a receipt-mode forger passes them — limit 6 declares this for `--receipt` mode, and the claim's counting command is `--live`. My mutations above confirm the live-only bindings still hold on the scored receipt (ports/missing/tmpdir all matched live run). The counter checks `missingExists === false` strictly and `missingPath` basename; `libs`/`files`/`payloads` use deep `JSON.stringify` equality, so type-coercion forgeries (0/"0", missing fields) fail. No null-passes finding.
5. **Battery `rePort` rewrite — correct.** It rewrites ONLY every occurrence of `:<from>/` inside `JSON.stringify(legs)` (negatives L38-44): receipt `ports` value set to the forged number, all leg URLs rewritten consistently, so only the `ports` range check can see it. Unqualified rewrite of an embedded UUID/port inside a string elsewhere is not possible (it splits on `:<port>/`, and no other leg string contains that pattern). Cases `port-1023`, `port-65536`, `port-fractional` are killed, confirming the R98Mut survivors are dead this round.
