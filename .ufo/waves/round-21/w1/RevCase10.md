# RevCase10 — `na-invalid-submit`

## Reconstructed axes

1. **Input conversion** — does the invocation payload fail `FillData`, or does it successfully set a value that is invalid under the form's HTML constraints?
2. **Entry-time autosubmit** — does `ExecuteTool` submit immediately, or leave the active invocation waiting for an action?
3. **Submit dispatch and callback** — does interactive validation stop the path before a page `submit` event, and which completion channel is then reachable?
4. **Promise versus native navigation** — can `SubmitEvent.respondWith()` settle, or does Blink schedule form navigation?

## Source contract and evidence chain

The primary source is the reopened round-20 snapshot `corpus/evidence/round-20/sources/html_form_element.cc` (`[html_form_element.cc#A286]`). Line references below are to that tagged file.

- **Conversion precedes tool activation.** `HTMLFormMcpTool::ExecuteTool` derives `require_submit_button` from the presence of `toolautosubmit`, then calls `FillFormControls` before setting `is_currently_running_`, marking the active form/button, or moving `done_callback_` into `done_callback_` (174–221). `FillFormControls` parses JSON, requires an object, finds the submit button, and calls `FormMCPSchema::FillData`; a conversion error runs the callback directly and returns before the active/waiting state (231–259, 196–198).
- **Conversion is not HTML constraint validation.** The retained round-19 `form_mcp_schema.cc` source (`form_mcp_schema.cc.gz:form_mcp_schema.cc:208–245`) validates supplied parameter names/types/values, then applies them. Its text-fill path sets the control value (930–948). Round-19 observations separate these cases: `{}` for a required text field successfully reaches `toolInvoked`, leaves the field empty, then returns `Error` with `Form validation failed: required: Please fill out this field.. ` and has no submit-listener calls (`validation/probes/missing-required.json:34–98`); `{"required":null}` instead returns `Invalid value for parameter required` while leaving the control unchanged (165–229). A string `q:"abc"` likewise reaches `toolInvoked` and leaves `abc` in the input, but the browser reports `patternMismatch` and a form-validation error with no page submit callback (`validation/probes/text-constraints.json:46–104`; fixture constraint at `validation/fixtures/text-constraints.html:5–7`). Thus an omitted required value or a string that violates `required`/`pattern` is not itself a JSON-conversion failure.
- **The non-autosubmit branch waits.** After successful fill, Blink sets the tool running, sets the active pseudo-state, stores the completion callback, focuses the submit button, and pauses model-context execution when `toolautosubmit` is absent (204–217). Only the `toolautosubmit` branch immediately calls `PrepareForSubmission` (219–220). The entry-time submit is therefore not expected for a successful non-auto invocation.
- **Interactive validation precedes submit-event dispatch.** `PrepareForSubmission` calls `ValidateInteractively` before constructing/dispatching `SubmitEvent` (713–776). If invalid, it sets `should_submit=false`; for a currently running declarative tool it constructs `Form validation failed: <parameter>: <validationMessage>. ` and calls `CallDoneCallback` with `kToolInvocationFailed` (729–759). The event-dispatch and `respondWith` processing is in the `else` branch (760–816), so this invalid path has no page `submit` event, no `TakeRespondWithPromise`, and no `HandleWebMcpToolResponse` settlement. `CallDoneCallback` consumes the once-callback and clears running/active state and invocation id (261–275).
- **Navigation is not scheduled on that invalid branch.** `ScheduleFormSubmission` is reached after dispatch only when `should_submit` is true (818–830); invalid validation leaves it false. If a valid dispatched submit is not canceled, that path schedules submission and resolves the still-running tool with a null string indicating navigation (824–830). By contrast, the separate `submitFromJavaScript()` path calls `ScheduleFormSubmission` directly and resolves a running tool (834–842); it is not evidence that an invalid click/requestSubmit navigates. The source explicitly shows `requestSubmit()` forwarding to `PrepareForSubmission` (845–873).

## What the legacy probes establish

- Round-19 `missing-required` fixture is `toolautosubmit` and has a required input plus a `submit` listener (fixture lines 8–25). With input `{}`, the probe reports `WebMCP.toolResponded` `status: Error`, `submitCount: 0`, and `calls: []` (probe lines 34–98). This is strong precedent for the validation-error callback and no submit dispatch, but it exercises **entry-time autosubmit**, not the no-auto wait branch.
- Round-19 `text-constraints` similarly establishes that a string can be accepted and applied yet fail browser validity before the submit listener runs (probe lines 46–104). Its other `minlength` case (`AB`) is accepted and dispatches the submit listener (120–197), helping distinguish a real constraint failure from mere schema metadata.
- Round-17 `invoke-declarative-form` is the contrasting successful promise path: its fixture sets `toolautosubmit`, then the page listener calls `preventDefault()` and `respondWith(Promise.resolve(...))` (fixture lines 6–45); the recorded event has `agentInvoked:true`, the invocation completes `Completed` with the promise result, and navigation count is zero (receipt case `invoke-declarative-form`). Round-17 `invoke-declarative-navigation-result` is the contrasting native-navigation path: an unprevented valid auto-submit requests and completes navigation, then the invocation completes from the landing document (receipt control `invoke-declarative-navigation-result`). Neither is the invalid-before-dispatch path.

## Case-specific expectation — inference, not a round-21 observation

**Assumption:** I read `na-` as the no-`toolautosubmit` family described by the round-21 contract, and `invalid-submit` as a post-invocation user submit action against a control that remains HTML-invalid. The exact round-21 fixture, invalid control/value, and action call are not in the legacy evidence inspected here; therefore exact parameter name, validation text, and action-to-`PrepareForSubmission` call route remain unobserved.

If input conversion succeeds but leaves an invalid required/pattern-constrained control, the predicted evidence sequence is:

1. `WebMCP.invokeTool` is accepted and a correlated `WebMCP.toolInvoked` carries the invocation input. Before the separately-triggered action, the tool should remain active (`:tool-form-active`), the submit button should be focused, and there should be no matching `toolResponded` or submit/navigation side effect. This follows the no-auto branch at 204–217; the finite pre-action observation window is measurement evidence, not proof of universal pending behavior.
2. The post-invocation invalid submit should take the validation-error branch: one correlated `WebMCP.toolResponded` with `status: Error` and an `errorText` formed from the invalid parameter name and the control's current validation message; no page `submit` listener call/event; no `respondWith` promise; no form-navigation frame. After callback completion, the tool active state should be cleared. Round-19's error status and no-submit observations corroborate this translation, but are not a round-21 run.
   This prediction assumes interactive validation is enabled. `PrepareForSubmission` skips it for form `novalidate` or submitter `formnovalidate` (713–715); those flags would make an invalid control insufficient to predict this error path and could allow submit dispatch/navigation.
3. If the invalid value is instead rejected by `FillData` (e.g. a JSON `null` where text is expected), that is a different outcome: immediate input-argument error before active state/callback storage and before the non-auto wait/action. The round-19 `null` case is the precedent. An omitted required key is not such a conversion error: the required field can remain empty and fail only when validation is attempted.

The above prediction does **not** apply if the action actually invokes `form.submit()` rather than a normal submit attempt/`requestSubmit()`: the retained source exposes a direct `submitFromJavaScript()` → `ScheduleFormSubmission()` route that bypasses this `PrepareForSubmission` validation/event path. Round-21's separate `na-native-submit` case suggests that distinction is intentional, but that mapping is an inference from case naming, not observed evidence. Preserve the runtime's actual action and raw CDP result rather than predicting it away.

## Confidence and limits

- **High** for the source-level order: JSON conversion → active/no-auto wait or entry-time auto-submit → interactive validation before event → callback error versus promise or scheduled navigation. Primary evidence is the tagged round-20 source.
- **High** that prior round-19 runs observed conversion-invalid versus HTML-invalid outcomes separately, with no submit callback for validation failures.
- **Medium** for the predicted round-21 `Error`/zero-submit/zero-navigation outcome, conditional on the case being a normal invalid submit after successful conversion. No `na-invalid-submit` runtime observation was made here.
- **Uncertain** exact input, invalid field/message, action primitive, and whether round-21 measures validation UI details; none follows from the legacy fixtures alone.
- The connected tool inventory has no `lsp` device; `read xd://lsp` returned “No such tool.” Source was read directly; literal grep was used only to locate source text, not as semantic call-graph proof. No experiment was run and no code was changed.
