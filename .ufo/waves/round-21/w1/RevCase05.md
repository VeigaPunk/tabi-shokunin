## Reconstructed call path

1. **Input conversion and fill.** `ExecuteTool` receives `input_arguments` as a Blink `String`. `FillFormControls` parses it as JSON, requires a `JSONObject`, obtains the schema submit button, and calls `FormMCPSchema::FillData` (174–197, 231–259). In the current fixture the WebMCP input is an object with string property `q`; `toolInvoked.input` is its JSON-string form. The conversion from CDP's object to the Blink string and the per-control fill implementation are outside this file. The retained round-17 probe documents the object-to-string `toolInvoked` boundary (C2ProbeDeclarative.md:51–53); round-19's validation note describes fill-time versus submit-time validation, but is not a reset witness.

2. **Entry-time autosubmit decision.** The fixture has no `toolautosubmit`, so `require_submit_button` is computed true at invocation entry (181–186). After successful fill, the tool is marked running, the submit button is stored as active, the callback is stored in `done_callback_`, and the form/button pseudo-states are changed (200–210). The no-autosubmit arm focuses the submit button and pauses execution (212–217); it does **not** call `PrepareForSubmission`. The fixture's submit button is present; the current capture records focus on `go` and `formActive:true` before the action.

3. **Submit dispatch is a separate path.** A submit event is created and dispatched only inside `PrepareForSubmission` (760–776). For an active declarative invocation, that event is marked `agentInvoked`; a `respondWith` promise is then taken and attached to `HandleWebMcpToolResponse` (769–806). The case's page listener is a `submit` listener, not a `reset` listener. A reset does not itself dispatch this submit event, so the listener's `preventDefault()` and success-mode `respondWith(Promise.resolve(...))` are not reached. Thus `na-reset` does not settle through the page promise. Its pending callback is settled by the reset-specific cancellation call below.

4. **Reset and callback storage/settlement.** `HTMLFormElement::reset()` returns immediately only for re-entry or a missing frame (1077–1080). Otherwise it dispatches a **cancelable bubbling `reset` event**; if canceled, it clears the guard and returns before resetting controls or canceling the WebMCP tool (1082–1088). On the non-canceled path it resets each listed form control (1090–1099), then, if `active_webmcp_tool_` is present, calls `CallDoneCallback` with `kToolCancelled` and the literal `Tool execution cancelled by a form reset` (1101–1105). `CallDoneCallback` returns if no callback is stored; otherwise it runs the stored callback before clearing running/button/invocation state and updating pseudo-states (261–275). For the successful, active invocation represented by this fixture, the source-level result is therefore cancellation, not promise resolution.

5. **Native navigation.** Neither the reset branch nor the no-autosubmit entry branch calls `PrepareForSubmission`/`ScheduleFormSubmission`. Native form navigation is scheduled only on the submission path (818–830), not by the reset method. The fixture's `/landing` action is consequently not used by the reset itself. A page reset handler could independently submit or navigate, but this fixture has no reset handler; do not generalize the no-navigation result to arbitrary pages.

## Case-specific expected evidence

The contract's pre-action sample is bounded: no matching response during that interval means only “no response in this window,” not indefinitely pending. For this case, expected evidence after a successful invoke and before reset is: `invokeTool` result with an invocation ID; `toolInvoked` with the same ID and JSON-string input for `q`; no submit record; the filled `q`; active form and focused `go`; and zero matching responses within the named pre-action window. After the non-canceled reset, the expected source-level outcome is one cancellation settlement for that same ID, a cleared form-active state, and controls returned to defaults. No submit-handler record, `respondWith` settlement, or native `/landing` navigation should be attributed to this action.

## Last-known-good comparison, divergence, and uncertainty

The retained round-17 probe (`.ufo/waves/round-17/w1/C2ProbeDeclarative.md:42–50, 71–73`) observed no `toolResponded` for 2,500 ms after a no-autosubmit invoke with no submit, then observed completion after page `requestSubmit()`. That is the last-known-good bounded pending behavior, not an indefinite-pending guarantee and not evidence that only a human can submit. `na-reset` differs for a concrete reason: reset has its own explicit cancellation branch, so “no submit yet” must not be conflated with “reset leaves the invocation pending.” The r17 requestSubmit probe is adjacent history, not a reset test.

**Confidence:** high for the pinned C++ branch and callback ordering; the retained source is a tag-pinned body. The fixture has no reset listener and the current capture shows the tool active before reset, satisfying the relevant case conditions. Uncertainty remains that (a) a canceling reset listener would bypass both control reset and WebMCP cancellation; (b) `HTMLFormControlElement::Reset()` internals are outside this source range, so the empty default for `q` follows from the fixture's missing value attribute and is also directly observed in the retained capture; (c) this file supplies the internal `ScriptToolError`, not the CDP status/event mapping or delivery timing—the `Canceled` wire event is an observation from the current capture; and (d) all claims are limited to this Chromium build, fixture, and finite observation windows.
