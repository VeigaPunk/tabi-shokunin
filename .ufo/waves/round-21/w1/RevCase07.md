# RevCase07 — `na-reject` source reconstruction

## Contract and last-known-good invariant

**Case-scoped source contract:** Given a valid object for a connected non-`toolautosubmit` declarative form with a recognized submit button, `ExecuteTool` fills controls and stores the invocation callback, marks the tool active, focuses the button, and pauses ModelContext execution; it does not submit merely because the tool was invoked. If the later submit event is canceled and supplies `respondWith()` with a promise that rejects while the tool is still running, Blink attaches a rejection handler. That handler reports the rejection value and calls the stored callback with `kToolInvocationFailed` and the fixed message `respondWith promise was rejected`. This submit branch does not schedule native form submission.

This is conditional on the intended fixture actually reaching the submit handler and on `preventDefault()` preceding a successful `respondWith()` call. It is Chromium 154 source behavior, not a WebMCP-wide guarantee or a new runtime observation. `html_form_element.cc` does not establish the eventual CDP `toolResponded` status, its exact fields, or settlement timing; record those from the raw frames rather than treating them as source predictions.

**Last-known-good comparison:** The round-17 no-autosubmit probe observed no submit or `toolResponded` during its 2500 ms initial window, then its page-side `requestSubmit()` caused an `agentInvoked` submit and completion through a resolving `respondWith()` promise. It also observed `preventDefault()` without `respondWith()` returning a distinct programming-error result. These establish neighboring paths only: round 17 did not test a rejected declarative `respondWith()` promise. No round-21 `na-reject` runtime result is available in this report, so there is no measured divergence to state.

## Execution chain

1. **Input conversion and fill.** `ExecuteTool` receives an invocation id and a Blink `String input_arguments`; `FillFormControls` parses that string as JSON, requires an object, obtains the form's submit button, rejects a missing button when `toolautosubmit` is absent, then calls `FormMCPSchema::FillData` (`html_form_element.cc:174-198,231-259`). The source span does not show the upstream CDP-object-to-string conversion. Round 17 observed `WebMCP.invokeTool` take an object while `toolInvoked.input` was a JSON string. Use valid case-fixture input: a parse/object/fill error calls the incoming callback before the successful active-state assignments, and is not the rejection path (`:196-198,204-210`).

   Round-19 controls help separate these failures from submit-time handling: `unknown-param` observed a fill-time `Error`, zero submits, and unchanged fields (`corpus/evidence/round-19/validation/receipt.json`, `decl-unknown-param-01`); `missing-required` observed native validation returning `Error` with `submitCount: 0` before the listener (`…/receipt.json`, `decl-missing-required-01`). Both are `toolautosubmit` validation controls, not `na-reject` witnesses.

2. **Entry-time `toolautosubmit` decision and callback storage.** At entry Blink sets `require_submit_button = !FastHasAttribute(toolautosubmit)`. On successful fill it marks the tool running, sets the active submit button/form pseudo-state, and stores `done_callback_`. The no-autosubmit branch focuses the button and calls `PauseExecution()`; the sibling autosubmit branch calls `PrepareForSubmission(nullptr, submit_button)` immediately (`:181-221`). Thus the `na-reject` rejection promise cannot arise at invocation entry: it requires a later submit event. The form must have a submit button for this no-autosubmit entry path (`:249-258`).

3. **Submit dispatch.** A later submit enters `PrepareForSubmission`. It can return early for frame/state/connectivity/sandbox/blocking conditions; otherwise it performs interactive validation before dispatching the submit event (`:635-694,713-760`). While the declarative tool remains running, Blink sets `SubmitEvent.agentInvoked` to true, dispatches the event, and derives `should_submit` from whether dispatch was canceled (`:720-776`). This does not require a human: page-script `requestSubmit()` reaches `PrepareForSubmission` too (`:845-873`), and the round-17 no-autosubmit probe observed that page-script route while an invocation was active. Do not label script submission human-only.

4. **`respondWith` registration and promise settlement.** If the event listener calls `preventDefault()` and supplies a promise, `TakeRespondWithPromise()` returns it; Blink checks that `should_submit` is false and attaches resolve/reject handlers (`:787-806`). For a still-running tool, the rejection handler enters `HandleWebMcpToolResponse(resolved=false)`, reports the rejection value with `V8ScriptRunner::ReportException`, then calls `CallDoneCallback` with `kToolInvocationFailed` and `respondWith promise was rejected` (`:290-328`). `CallDoneCallback` returns without cleanup if its stored callback is null; otherwise it invokes the callback and then clears the running state, active button, and invocation id (`:261-275`). The C++ method call is the source fact; callback delivery and any wire representation remain downstream.

   `respondWith()` must follow `preventDefault()`: the r17 fixture records `InvalidStateError` when it is called first, then succeeds after cancellation (`.ufo/waves/round-17/probes/invoke-declarative.mjs:150-163`; `.ufo/waves/round-17/w1/C2ProbeDeclarative.md:74-76`). The `na-reject` listener must therefore make the order explicit and record whether the call was accepted; otherwise it may test the wrong branch.

5. **Native navigation.** With a promise taken, the source requires `!should_submit`; the subsequent `if (should_submit)` block is skipped, so this path does not call `ScheduleFormSubmission` or the navigation-intent callback at `:818-830`. `ScheduleFormSubmission` is the separate native scheduling path (`:882-1042`). This excludes native form submission through the canceled `respondWith` branch, not unrelated page-triggered navigation or effects outside this file. In particular, do not confuse it with the distinct `form.submit()`/`submitFromJavaScript()` path (`:834-842`), which bypasses submit-event handling.

## Concrete evidence to retain for `na-reject`

- Preserve the raw `WebMCP.invokeTool` send/result, the returned `invocationId`, and the correlated `WebMCP.toolInvoked` frame. Round 17 observed the command input as an object and `toolInvoked.input` as a JSON string; those are distinct representations and should not be conflated.
- Keep the bounded pre-action observation separate from the later action. It should document its finite `windowMs`, raw response count for that invocation id, form-active/page state, and unchanged fixture identity. A zero pre-action response is only “none observed in this interval,” not cancellation or a permanent pending status.
- After the case action, retain ordered CDP frames and page observation for the actual submit event: whether it was reached, `agentInvoked`, `defaultPrevented`, the listener's `respondWith` call/acceptance, and any page-owned dummy input/rejection marker. Record actual evidence rather than asserting a trusted event or a particular trigger from source alone.
- Correlate any eventual `WebMCP.toolResponded` only by the invocation id, retaining its observed status, `errorText`, `output` presence/absence, and timestamp/order. The source supports an internal rejection error callback but does not prove that the protocol emits `status: "Error"`, which error text it exposes, or when it arrives. Round 17's `Error` for preventDefault-without-respondWith is a different branch; its imperative `execute()` rejection case is also not a declarative `SubmitEvent.respondWith()` rejection.
- Record navigation/frame-change and loopback form-action request evidence independently. No such event is expected from the canceled promise branch itself, but a runtime absence is a bounded observation, not a source guarantee about unrelated page code.
