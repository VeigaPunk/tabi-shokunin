# RevCase06 — `na-remove` source reconstruction

## Scope and assumptions

This is a source-only reconstruction of fixed case `na-remove`, using the retained Chromium 154.0.8037.97 body `corpus/evidence/round-20/sources/html_form_element.cc` (SHA-256 `8c8d6796b17bf8e8348747386c0d8720815b3d7df6d0bc4de0f3d3d4b8c36916`). It is not a new browser observation. The predicted branch assumes WebMCP is enabled, the connected form has `toolname` and `tooldescription`, the form has a recognized submit button, the valid object input fills successfully, and the form is removed only after the required bounded pre-action observation. The no-submit pre-action assumption matters: if the page has already entered submit handling, the removal branch has a different guard.

**LSP availability:** `read xd://lsp` returned “No such tool”; no LSP references/definition/implementation server was mounted. Literal search was only a locator fallback; the semantic claims below are grounded in the displayed retained source spans, not grep as proof. This does not establish the absence of other callers outside this source file.

## Contract and last-known-good comparison

For the intended `na-remove` preconditions, Blink should first hold a running declarative invocation with its callback stored and no submit dispatched by invocation. Removing the connected form then makes its declarative-tool definition invalid. In `ScheduleDeclarativeWebMCPToolRegistration`, when the active tool is not handling a submit, the source calls `CallDoneCallback` with `kToolCancelled` and the literal `Tool execution cancelled, since tool definition was updated`, then calls `UnregisterTool` and clears `active_webmcp_tool_` (`html_form_element.cc:350-399`, reached from `RemovedFrom` at `:486-524`). Since the no-autosubmit entry branch only focuses the submit button and pauses ModelContext execution, it does not itself dispatch a submit (`:181-221`). Thus the expected source path is removal-triggered tool cancellation, not submit-event `respondWith` settlement or native form submission.

The closest prior no-autosubmit probe is not a removal test: round 17 recorded no submit and no `toolResponded` during the initial 2500 ms window, followed by a page-side `requestSubmit()` and completion (`.ufo/waves/round-17/w1/C2ProbeDeclarative.md:42-49,71-73`). This is a bounded pending observation, not an indefinite-pending guarantee or a claim that only a human can submit. Round 17's `invoke-unregister-while-pending` was an **imperative** tool; it observed `toolsRemoved`, then `Completed` after the pending execute returned (`.ufo/waves/round-17/w1/C2ProbeLifecycle.md:44-47`). That is not the declarative form-removal branch: this source explicitly tries to cancel the declarative invocation before unregistering it. The r19 validation fixtures/receipt are autosubmit input/constraint cases, not form-removal evidence; for example `decl-missing-required-01` observes a submit-validation `Error` with zero submit events, a distinct branch (`corpus/evidence/round-19/validation/receipt.json`, case `decl-missing-required-01`).

## Source trace, separated by stage

1. **Input representation and fill.** Round 17's recorded `WebMCP.invokeTool` request passes an object, while `toolInvoked.input` is a JSON string (`corpus/evidence/round-17/webmcp-invoke/receipt.json`, `invoke-declarative-form`). The upstream conversion between those forms is outside this retained C++ span. Here `ExecuteTool` receives a Blink `String input_arguments`; `FillFormControls` parses JSON and requires an object, gets the submit button, and calls `FormMCPSchema::FillData` (`html_form_element.cc:174-198,231-259`). For this case, use a valid dummy object such as `{q: nonce}` and retain the exact command input and `toolInvoked.input` rather than conflating their types. Parse/object/fill errors return through the incoming callback before running-state and stored-callback assignments; a missing submit button is an early error when autosubmit is absent (`:196-210,249-258`).

2. **Entry-time `toolautosubmit`.** At `ExecuteTool` entry, `require_submit_button` is computed from the form's current `toolautosubmit` attribute (`:181-186`). With that attribute absent, it is true. This is distinct from input parsing and from the prior registration-time annotation. A valid no-autosubmit fixture therefore needs a submit button (`:249-258`).

3. **Submit dispatch and callback storage.** After successful fill, the code marks the tool running, marks the form/button pseudo-states, and stores `done_callback_` (`:200-210`). With `require_submit_button` true, it calls `submit_button->Focus()` and `context->PauseExecution()`; it does not call `PrepareForSubmission` in this branch (`:212-221`). Effects inside focus/pause are not established by these lines. A later page `requestSubmit()` can enter `PrepareForSubmission` while the invocation remains active; the r17 probe observed this, so script submission must not be described as human-only.

4. **Removal and callback delivery.** `RemovedFrom` schedules declarative registration handling when the removal is from a connected insertion point (`:518-524`). With WebMCP enabled and a frame present, the now-disconnected form fails `isConnected() && name && description`; the removal path cancels pending registration. If an active tool exists and `IsHandlingSubmit()` is false, it calls `CallDoneCallback(base::unexpected(ScriptToolError(kToolCancelled, ...)))`, unregisters the tool name, then nulls the active-tool pointer (`:353-399`). In the intended pre-action state—invocation active, no submit underway—the stored callback exists from step 3 and the not-handling-submit arm is the expected one. `CallDoneCallback` itself returns without cleanup if that stored callback is null; otherwise it runs the callback first, then clears running state, active submit button, and invocation id and updates pseudo-state (`:261-275`). This establishes a C++ callback invocation and internal cancellation error, **not** a particular CDP result, event order, or delivery time.

5. **Promise settlement.** `SubmitEvent.respondWith()` is not the cancellation mechanism for this path. The promise-take/resolve/reject handling is attached only after `PrepareForSubmission` dispatches a submit event (`:769-806`; handler at `:290-328`). With the no-autosubmit invoke path and no intervening submit, there is no submit event promise to take or settle. If the page submits before the remove action, the case no longer satisfies this precondition and must be interpreted from its actual frames/page record.

6. **Native navigation.** The no-autosubmit branch does not reach `ScheduleFormSubmission`; the removal code unregisters the tool and does not schedule a form submission (`:212-221,378-399,818-830`). Therefore this source path predicts no form-action navigation caused by the removal itself. It does not prove that unrelated page code cannot navigate. Any navigation or absence of navigation must be recorded as the finite observed CDP/page/server result, not inferred from the cancellation callback.

## Concrete evidence for this case

Keep the stages separate in the per-case JSON:

- **Before removal:** raw `WebMCP.invokeTool` request/result; returned invocation id; correlated `toolInvoked` frame with matching id, tool/frame identity, and input string; page observation of the dummy filled value and form-active state; submit count; and the exact finite `preAction.windowMs` and matching-response count. The intended source path has the tool active and has not dispatched a submit. A zero response count means only no matching response in that interval.
- **Action:** record that the page-side `form.remove()` action was actually dispatched and observed, along with the form's resulting disconnected state if available. Keep the served fixture digest and run nonce so the removal is tied to this case.
- **After removal:** preserve ordered raw CDP sent/received frames and page observation. Correlate any `toolResponded` only by the original invocation id, retaining the observed status and exact `errorText`/`output` presence. The source-level expected callback argument is `kToolCancelled` with the definition-updated message; do **not** fabricate `status: Canceled`, an `errorText` mapping, or a response deadline from that C++ value. Record any `WebMCP.toolsRemoved` event if present—the retained source calls `UnregisterTool`, but this file does not show the wire event mapping. Record submit count and navigation/frame-change/server-request evidence independently; a finite absence is not a universal absence claim.

## Confidence and uncertainty

**High confidence** in the conditional Chromium source sequence: entry-time no-autosubmit selection; successful-fill state/callback storage; focus/pause without a direct submit call; and, for a disconnected active tool not handling a submit, a cancellation callback call followed by unregistration and active-pointer clearing. **Unresolved from this source-only trace:** whether the end-to-end fixture reaches those preconditions; exact callback-to-CDP status/error/output mapping and event ordering/timing; and any unrelated page-script effects. Round-17 no-autosubmit and imperative-unregister observations are contrasts, not witnesses for this declarative removal case. No experiment was run, no code was added, and no tools were installed or updated.
