# `na-native-submit` — source reconstruction

## Reconstructed contract

This case is a **non-autosubmit invocation followed by `HTMLFormElement.submit()`**, not a submit-button click or `requestSubmit()`. The runner executes `document.querySelector('#f').submit()` only after the bounded pre-action observation (`scripts/webmcp-lifecycle-round21.mjs:14-27, 153-171`). That API path bypasses the page's `submit` listener. Consequently, the fixture's `preventDefault()` and `respondWith(Promise.resolve(...))` are not the result path for this case; the form's GET submission navigates to `/landing` instead.

## Evidence chain

1. **Input conversion.** The runner sends `WebMCP.invokeTool` with `{q: nonce}`; the corresponding `WebMCP.toolInvoked` frame carries the serialized JSON string `{"q":"<nonce>"}`. In `html_form_element.cc`, `ExecuteTool` passes the supplied string to `FillFormControls`; that method parses JSON, requires an object, obtains the form schema and calls `FillData` (`round-20/sources/html_form_element.cc:174-177, 231-259`). The case's raw pre-action page observation has the nonce in the `q` control (`round-21/runtime/na-native-submit.json`, `frames` and `pageObservations`). This is input-to-control filling, distinct from later form-data construction. As a bounded cross-check on conversion, the r19 number probe records JSON number `42` in `toolInvoked.input` and the submitted field as string `"42"` (`round-19/validation/probes/number-type.json:267-301`); that does not imply extra coercion for this case's already-string `q`.

2. **Entry-time `toolautosubmit`.** The case has `autosubmit:false`, and its fixture has no `toolautosubmit` attribute (`scripts/webmcp-lifecycle-round21.mjs:14-18, 59-68`; `corpus/evidence/round-21/runtime/na-native-submit.html:1-17`). `ExecuteTool` reads the attribute at entry and therefore requires a submit button. On successful fill it marks the tool running, stores the invocation callback, marks the form/button active, then focuses the button and pauses execution; it does **not** call `PrepareForSubmission` on this branch (`round-20/sources/html_form_element.cc:174-221`). The retained pre-action observation matches that state: form active, focus on `go`, filled nonce, no submit recorded. The runner's pre-action response count is measured after its 250 ms wait (`scripts/webmcp-lifecycle-round21.mjs:155-159`). “No response” here is only the absence of a matching response in that finite window, not an indefinite-pending claim. R17's no-autosubmit fixture/case likewise treats it separately and marks `ifNoSubmit` (`.ufo/waves/round-17/probes/invoke-declarative.mjs:194-198, 617-618`).

3. **Submit dispatch: distinguish the three actions.** The runner maps this case's `action:'submit'` to `page.evaluate(() => document.querySelector('#f').submit())`; adjacent cases use a button click or `requestSubmit()` (`scripts/webmcp-lifecycle-round21.mjs:14-18, 160-167`). In Blink, the direct JS method path is `submitFromJavaScript()`, which calls `ScheduleFormSubmission(nullptr, nullptr)` rather than `PrepareForSubmission()` (`round-20/sources/html_form_element.cc:834-843`). In contrast, the click / `requestSubmit()` path enters `PrepareForSubmission()`, where interactive validation and `SubmitEvent` dispatch occur; the `agentInvoked` flag is set there for a currently running declarative tool (`:635-776, 845-873`). Thus this direct `.submit()` call does not dispatch the fixture's `submit` listener and does not enter the `respondWith` handling below. Do not infer `agentInvoked:false`: there is no `SubmitEvent` observation from which to read that property.

4. **Callback storage and settlement.** The callback is stored in `ExecuteTool` as `done_callback_` after filling succeeds (`:200-210`). The `respondWith` promise path exists only after `PrepareForSubmission()` dispatches a submit event, takes its response promise, and attaches resolve/reject handlers (`:789-815`). Its resolved-object JSON serialization and rejected-promise error behavior live in `HandleWebMcpToolResponse()` (`:290-327`). They are not reached by this case's direct `.submit()` call because that call bypasses submit-event dispatch. Instead, `submitFromJavaScript()` schedules the form submission, then calls the still-running tool callback with `base::ok(String())` (`:834-843`); `CallDoneCallback()` invokes the stored callback and clears running/invocation/active-button state (`:261-274`). The nearby `PrepareForSubmission()` comment describes a null string as the navigation-triggered signal (`:824-830`).

5. **Native navigation.** `ScheduleFormSubmission()` constructs the form submission from the form attributes with no event or submitter, then schedules it for the target frame after its connection, frame, sandbox, action, and navigation-policy checks (`:882-1043`). The fixture's action/method are `/landing`/`get`; form-data construction includes enabled listed controls (`:1045-1075`). The retained raw frames show navigation to `/landing?q=<nonce>` followed by one `WebMCP.toolResponded` with status `Completed` and output `[{"dummy":"landing"}]` (`corpus/evidence/round-21/runtime/na-native-submit.json`, `frames`). The after-action page observation is the landing URL with the original form absent (`same file`, `pageObservations`). These are observed facts, not source-only predictions.

## Prior probe contrast and divergence

The r17 `invoke-declarative` fixture uses `toolautosubmit`; its handler calls `preventDefault()` before `respondWith(Promise.resolve(...))` (`corpus/evidence/round-17/webmcp-invoke/fixtures/invoke-declarative.html:6-8, 40-46`). Its receipt records a trusted `SubmitEvent`, `agentInvoked:true`, no navigation, and `Completed` with the handler's object (`corpus/evidence/round-17/webmcp-invoke/receipt.json:4277-4288, 4316-4341`). That is the `PrepareForSubmission()`/promise branch, not this case's direct `.submit()` branch. Conversely, r17's separate unprevented autosubmit navigation fixture/result records a landing-document result (`fixtures/invoke-decl-nav.html:6-8, 39-41`; `receipt.json:8358-8371`). It is useful precedent, but differs in entry path.

There is **no observed source/runtime contradiction** once the action is traced correctly: the event handler's promise is unreachable, while direct form submission navigates, matching the retained case frames. The mapping from this translation unit's null-string callback signal to the observed landing-document output is not fully established by `html_form_element.cc` alone. The r17 navigation result and the current case's raw `toolResponded` frame support a navigation-result interpretation; the callback bridge/landing-result selection is outside this file and remains an inference here. Scheduling also depends on the source's ordinary connected-frame, sandbox, action, and target-navigation conditions; the retained navigation proves they permitted this recorded run, not that all forms do.
