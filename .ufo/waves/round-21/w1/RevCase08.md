## Scope and provenance

## Case-level expected evidence and uncertainty

For this exact fixture and captured run, the evidence chain is: successful invocation/fill → bounded pre-action state with no submit/response → page `requestSubmit()` → canceled submit event with a synchronous page error → one correlated `toolResponded(Error)` from the no-promise programming-error path → no form navigation, and the tool-active state clears. The raw case retains the invocation ID, ordered CDP frames, fixture digest, page observations, and the receipt's measured windows. The observed pre-action window was 253 ms and after-action window 503 ms; the initial absence of a response is only the named finite window. The error response is already present after the action, so this particular captured case is not pending.

The main divergence risk is conflating three distinct outcomes: (a) synchronous listener throw after `preventDefault()` (this case: uncaught page error plus no-promise programming-error callback), (b) `respondWith(Promise.reject(...))` (separate `HandleWebMcpToolResponse` rejection path), and (c) throwing before `preventDefault()` (not this fixture and not established here; it can leave `should_submit` on a different branch). Likewise, `requestSubmit()` during an active tool is not the same path as native `form.submit()` or an autosubmit entry.

Confidence is **high for the source-branch reconstruction conditional on the stated branch conditions**, and **high for the finite recorded outcome of this one Chromium 154 loopback case** because the raw frames and page snapshots correlate by invocation ID. Confidence is not a universal lifecycle claim: S100 is one tagged source body, the bridge from renderer callback to CDP payload is outside the retained S100 excerpt, the form-field setter details are delegated outside this file, and no statement is made about other builds, handler ordering, durations, or later navigation after the recorded interval.
