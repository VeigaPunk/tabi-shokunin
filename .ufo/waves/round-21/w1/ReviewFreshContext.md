## Findings

### F1 — HIGH (interface, blocks the metric) — counter and runtime encode incompatible evidence shapes; a perfect run still evaluates exit 1
Failure shape: runtime executes cleanly, blobs are committed, `measure-c1.mjs` evaluate() emits findings on all 12 cases and exits 1 — pure schema contradiction, no behavioral signal. Exact contradictions, runtime line vs counter line:
- Frame `dir` taxonomy: runtime records only `dir:'sent'` and `dir:'received'`, with replies as `received '<method>:result'`/`'<method>:error'` rows (r21:469-490). Counter selects `dir==='result'|'error'` keyed by `frame.command === command` (m:319) — runtime frames carry no `command` field, so `invoke_identity` fires on every case; `dir==='event'` for toolInvoked/toolResponded (m:343-348) and `dir==='action'` (m:351-353) match zero runtime rows → `event_identity`, `order_mismatch :action-record` everywhere. Runtime keeps actions in `evidence.actions` + timeline, not `frames`.
- Timestamps: counter `isTime()` requires a number (m:104) and checks `frame.at` (m:236-243); runtime `at` is an ISO string (`new Date().toISOString()`, r21:452-459) — `order_mismatch :frames` and `:page-observations` on every case even though `monoMs` numeric fields exist.
- Windows: runtime `windowMs` is a monotonic delta (`pre.monoMs - preStartMono`, r21:790; `post.monoMs - actionStart`, r21:857) while `start`/`end` are `Date.now()` wall values (r21:785-787, 852-855); counter requires `windowMs === preEnd - preStart` (wall) and `pre.at === preEnd` (ISO string vs number) (m:361-375) → `window_mismatch` always.
- `evidence.mode`: counter requires it (m:253); runtime `makeEvidence` (r21:609-647) has no `mode` field (mode lives only inside fixture HTML) → `case_plan <id>:mode` ×12.
- Cleanup fields: counter wants top-level `evidence.browserPidsBefore` (m:416); runtime records `browser.pidsBeforeClose` (r21:703). Counter wants top-level `evidence.blocked` and `evidence.downloads` (m:427-430); runtime has `evidence.network.blocked` (r21:643) and no downloads record at all → `context_cleanup`, `boundary_violation` ×12.
- Receipt flags: runtime emits `[resolver, blink, --disable-extensions, enable]` order (r21:150-156, 46-49) vs counter's ordered `EXPECTED_FLAGS` `[enable, blink, resolver, --disable-extensions]` (m:90-95) checked with order-sensitive `isDeepStrictEqual` (m:171) → `environment` finding despite identical membership.
- Extra prefix entry: runtime writes `execution.json` into `--out` (r21:1021), i.e. under `corpus/evidence/round-21/runtime/`; counter's `REQUIRED_TREE_PATHS` (m:107-111) flags any other prefix entry as `case_set: unexpected runtime-prefix entry` (m:157-159).
Minimum acceptance: one written shared schema table (frame dir/method/command/reply encoding, timestamp field+type, window clock, evidence field names, receipt flags order, prefix tree set) that both files implement; falsifier = run counter's evaluate() over a receipt+evidence set produced by the current runtime and require zero shape-class findings (`invoke_identity`, `event_identity`, `window_mismatch`, `:frames`/`:page-observations` order, `case_plan :mode`, `boundary_violation`) before any behavioral claim.

### F2 — MEDIUM (seat core) — "fresh context per case" is not re-derivable at receipt level, and the counter never re-derives it from evidence
Failure shape: a mutant that reuses one profile dir for all 12 cases (or launches one context once) produces byte-identical receipt fields for `cases[]` (which carry only id/nonce/action/…); nothing in the receipt or the counter's finding set (`nonce_reused`, `context_cleanup`) distinguishes it, because nonce uniqueness is orthogonal to context freshness. The runtime does record per-case distinct material — `browser.argv` retains the full `--user-data-dir=<tmpdir>/tabi-r21-lifetime-*/<id>-profile` (r21:652, 705; only `effectiveFlags` strips it at r21:713), and per-case browser pids differ — so re-derivation is possible from committed evidence, but no check consumes it. Per-case env isolation (HOME/XDG_CONFIG_HOME/TMPDIR → per-case temp dirs, r21:164-171, 688) is recorded nowhere in evidence, so it is auditable only by reading code.
Minimum acceptance: counter check that the 12 evidence files' `--user-data-dir=` argv tokens are pairwise distinct, each ends `<id>-profile`, and each sits under a common `tabi-r21-lifecycle-` mkdtemp root; optionally runtime records profile/home dir basenames (non-absolute) in `evidence.browser` so the counter can also pin the temp-root shape.

### F3 — LOW — `cleanup.serverClosed` can be `true` when no server ever existed
Failure shape: infrastructure failure before `startFixtureServer` (e.g. `playwright_unresolved`, r21:975) → `closeServer(null)` returns `{closed:true, notStarted:true}` (r21:929) and r21:1003 sets `cleanup.serverClosed = true` — a summary claiming a close that never happened. Exit is still 1 (cases incomplete, r21:1018-1020), and `cleanup.server` retains `notStarted:true`, so it is re-derivable, but the boolean's semantics conflate "closed" with "nothing to close".
Minimum acceptance: `serverClosed` derived as `server !== null && closeCallback.closed && portProbe.refused`, or the boolean renamed/reported alongside `notStarted`.

### F4 — LOW — `cleanup.browserClosed` conflates cleanup with observation completeness
Failure shape: a case whose browser fully exited but whose observation is incomplete (invoke failed, or a window observation errored) forces `browserClosed:false` (r21:1005-1008 requires every case `observationComplete`), mislabeling a successful cleanup as failed; conversely a partial run's leftover browser also yields false — the flag can only under-report. Re-derivable from per-case `browserPidsAfter`, so impact is semantic, not evidentiary.
Minimum acceptance: derive `browserClosed` from per-case `browserPidsAfter.length === 0` across written evidence (plus zero `remainingPids`), keep `observationComplete` in `receipt.errors` only.

### F5 — INFO — na-delayed's after-window legitimately exceeds `observationLimitMs`; the receipt names the limit but not the exception
Failure shape: for `na-delayed`, the after phase includes the 250 ms delayed branch + release (r21:824-832), so `after.windowMs` (r21:857) will read ≫500 while `observationLimitMs: AFTER_ACTION_WINDOW_MS` (r21:858) and `timingWindows.afterActionObservationMs: 500` stay fixed — honest raw measurement, but any reader (or future counter check) comparing `windowMs ≤ observationLimitMs` concludes drift. `evidence.timing` records `delayedResponseMs`/release result (r21:827-831), so the material is present.
Minimum acceptance: `timingWindows` (or `evidence.timing`) states that na-delayed's after window extends past `afterActionObservationMs` by `delayedRespondWithControlMs` + release time; or record the delayed sub-window as a separate named interval.

### F6 — INFO — host temp absolute paths in committed evidence
`browser.argv` embeds `<tmpdir>/tabi-r21-lifecycle-*/…` per case (r21:705). Not secrets/session material; recorded here only because `effectiveFlags` (r21:713) deliberately strips the same token, so the two fields have inconsistent redaction postures in one artifact.

## Verified holds (not guessed passes — each pinned)
- Fresh browser + empty profile/home/tmp **per case**: per-case dirs created fresh under one per-run `mkdtempSync` root (r21:652-657, 981), `launchPersistentContext(profile)` per case (r21:683) — a distinct chromium process and empty profile per case, strictly stronger than "fresh context".
- No operator env reaches the browser: playwright-core 1.64.0 spawns with `env: options.env` verbatim (playwright-core/lib/coreBundle.js:10036) and uses the caller env only when provided, else `process.env` (:41217); chromium's `amendEnvironment` is spread-only (:52249-52254). So chromium sees exactly the six vars of `minimalBrowserEnv` (r21:164-171): HOME/XDG_CONFIG_HOME/TMPDIR point at per-case temp dirs; no DBUS_SESSION_BUS_ADDRESS, no XDG_RUNTIME_DIR, no operator HOME → no operator session/profile reads via environment.
- No state reuse surfaces: grep over the clone runtime finds no `storageState`, `cookies(`, `localStorage`, `addInitScript`, `newContext`, no operator `userDataDir` — the only `user-data-dir` occurrences are the per-case temp marker/ownership logic (r21:442-445, 699-705).
- r19 flag parity ("flags from r19"): byte-identical `HOST_RESOLVER_DENY` (r19:52 = r21:45), identical 17-entry disable list (r19:70-88 = r21:26-44), identical enable/blink sets, same merge/ignoreDefaultArgs scheme (r19:441-467 ≈ r21:146-162), same `minimalBrowserEnv` and launch options (r19:274-281, 543-556 ≈ r21:164-171, 683-696).
- Loopback-only: server binds `127.0.0.1:0` and rejects any other bind address (r21:315-321); per-case argv guard requires pipe debugging, zero `--remote-debugging-port` tokens, exactly one resolver token equal to the deny string, no DevToolsActivePort file, exact chromium version, sandbox kept (r21:714-733) and throws otherwise; request-level route guard allows only `http://127.0.0.1:<port>` without credentials and closes websockets (r21:344-360); `serviceWorkers:'block'` (r21:689).
- Non-auto action gating: action dispatch is skipped unless a non-empty `invocationId` exists with no invokeError (r21:754-758), and dispatch occurs only after the 250 ms bounded pre-action observation (r21:773-798 precede the action block at 800+).
- Cleanup even on error: per-case `finally` closes context/browser (owned-tree SIGTERM/SIGKILL with startTicks pid-reuse identity, r21:609-657 region + 873) and writes evidence (r21:881-884); run-level `finally` closes the server, probes the port, removes the temp root, and writes the receipt (r21:1002-1016). No operator file is written outside `corpus/evidence/round-21/runtime/` (path jailed by `assertOutputPath`, r21:181-190).
- Environment resolution: playwright 1.64.0 resolves on this host via the fnm node path that `candidatePlaywrightDirs()` index 0 covers (`~/.local/share/fnm/node-versions/v24.21.0/installation/lib/node_modules/playwright`, version read as 1.64.0); profile-boundary posture matches the r17-era knowledge rule (never point debugging at the default profile — fresh non-default `--user-data-dir` per case satisfies Chrome ≥136's gate regardless of branding, per `chrome-remote-debugging-profile-boundary.md` §1-§4).
