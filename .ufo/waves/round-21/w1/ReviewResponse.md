# ReviewResponse — toolResponded identity and outcome fields

## Findings

No actionable defect found in the current canonical round-21 response-correlation path.

The runtime obtains `invocationId` from the `WebMCP.invokeTool` result (`scripts/webmcp-lifecycle-round21.mjs:154-157`), then selects `WebMCP.toolResponded` records only where `params.invocationId === invocationId` (`:161`); the full matching `params` object is retained in `after.responses` (`:178`). The counter independently binds the receipt ID to that exact invoke-command result (`.ufo/waves/round-21/measure-c1.mjs:69-76`) and requires the receipt response summary to equal the raw `toolResponded` params filtered by that ID (`:74-76,85`). That preserves observed status/error fields without imposing an expected status, in line with the round-21 contract (`.ufo/waves/round-21/w1-spec.json:3`).

Raw evidence is consistent with that binding: for `na-reject`, the event at `corpus/evidence/round-21/runtime/na-reject.json:198-206` carries invocation ID `74F4E3D880F9F27879B61864414FBD25`, `status: Error`, and `errorText: "respondWith promise was rejected"`; the receipt entry at `corpus/evidence/round-21/runtime/receipt.json:341-363` has the same ID and payload. `na-throw` likewise records its own ID with the observed `Error`/programming-error text (`corpus/evidence/round-21/runtime/na-throw.json:198-206`). Read-only inspection of all 12 current case records found the recorded response IDs equal their receipt `invocationId`; `na-pending` has no matching response. The current acquisition is identified as qualified at `.ufo/waves/round-21/runtime-execution-final.json:15-18`; its producer digest matches the current runtime file.

This matches the prior protocol-evidence rule that an invocation outcome is linked by the same ID across `invokeTool`, `toolInvoked`, and `toolResponded` (round-17 note, `.ufo/waves/round-21/clones/BuildCounter/corpus/knowledge/webmcp-invocation-round-17.md:70-75`). Round 19 also treats `status` and `errorText` as observed fields (`.../webmcp-declarative-validation-round-19.md:69-72`). Round-20’s source-only caveat remains in force: source callsites alone do not establish runtime/CDP results (`.../webmcp-completion-lifecycle-round-20.md:100-106`).

Therefore the run itself does not demonstrate exclusion of a foreign response, even though the current runtime and counter implement the exact-ID filter.
