## Findings

1. **Attack: substitute a stale/different fixture or input nonce.** Observed: `corpus/evidence/round-21/runtime/na-invalid-submit.html:5,12` contains dummy nonce `4bc374a5-2705-4aae-a1ae-bd295b12b0fb`; its input starts empty and required (`:3`), rather than having an HTML value attribute. Thus the page echo alone is not mistaken for evidence of input fill: the separately recorded pre-action input value supplies that link. Current retained HTML SHA-256, computed with sha256sum, is `8a64d21d2b704dee05e8e734e4b9f381f0ff764f37931702d5fa47745d60be0e`, matching raw JSON `:8-10`. Raw JSON SHA-256 is `ca703c843237671ec435efd9797ff4e70e1e02884b714ef5f4e2c34e488919b0`, matching receipt `:567-569`. Confidence: high for retained-artifact consistency, not independently authenticated execution.

2. **Attack: metadata says non-autosubmit while actual markup enables autosubmit.** Observed: the actual form opening tag in HTML `:2` has no `toolautosubmit`; raw JSON `:5` and receipt `:531` say false. Producer `scripts/webmcp-lifecycle-round21.mjs:24,105-108` selects false/invalidRequestSubmit/success and emits the attribute only when autosubmit is true. Required text input, not malformed-email fixture (`html:3,10`). No attribute/metadata mismatch found in this case. Confidence: high.

3. **Attack: invalid initial invocation or wrong action is mislabeled submit-time invalidation.** Producer `:202-204` invokes with nonce for success mode and requires a nonempty invocation ID before acting; `:217` then sets q to empty and calls `requestSubmit()` in one page.evaluate callback. This is neither native `form.submit()` nor a Playwright click. Raw JSON `:167-224` shows pre-action active/filled/zero submits (seq12), invalidRequestSubmit dispatch-started (seq13), action-complete (seq14), matching Error response (seq15), then after-action empty input/inactive/zero submits/errors (seq16). Error text is `Form validation failed: q: Please fill out this field.. `. Receipt `:535-565` correlates 253ms initial observation and 502ms after-action window, no navigation. **Limit:** action markers name the action; they do not serialize the JavaScript expression or capture the empty value immediately before requestSubmit. The dispatch-started marker is appended after creating the page.evaluate promise (`producer:211,217-220`), so it is not a precise browser-side execution-start timestamp. The acknowledgement and post state support this bounded observation, not finer-grained timing. Confidence: high on retained sequence and producer mechanism; causal interpretation remains source-plus-own-work evidence.

4. **Attack: response is actually the success handler, or handler ordering is reversed.** HTML `:7-15` records submit first, calls preventDefault second, then constructs the value and calls respondWith(Promise.resolve(value)) in this success-mode fixture. Producer `:112-120` has the same order. But raw pre/post submit arrays are both empty (`json:174,215`), and response is validation Error, not dummy success. Therefore preventDefault/respondWith ordering is a fixture fact, **not an exercised handler-path observation in this case**. No handler invocation or dummy response nonce should be claimed here. Confidence: high; no browser execution conducted by this reviewer.

5. **Attack: reused host profile or PID-only cleanup falsely establishes isolation.** Producer `:128,159,164` creates a fresh temporary root and case-specific persistent profile; HOME/TMPDIR are temporary and acceptDownloads false. `:171-175` permits only same-origin GET requests, aborting others. `processTree` (`:52-64`) identifies exact user-data-dir roots and their descendants; launch records PID/startTicks (`:168-169`). Cleanup refreshes ownership before close, merges identities, bounds context.close to 5s, checks start ticks, rescans after close, and only SIGKILLs matching identities if needed (`:72-103`). Raw JSON `:260-362` records nine owned launch/close PIDs, matching start-tick identities, contextClosed true, no after-close owned PIDs, no remaining identities, no blocked requests/downloads, and no forcedCleanup field. **Limits:** profile pathname/effective Chromium argv are not retained in this per-case evidence, so fresh profile creation is supported by pinned producer logic rather than an independent profile/argv capture. /proc snapshots cannot rule out an unobserved descendant that reparented before discovery, nor prove host-wide or actor quiescence. No current process probe was performed. Confidence: high on recorded cleanup, bounded on exhaustive process isolation.

6. **Attack: retained hash is promoted into proof of bytes delivered, or upstream source is promoted into binary equivalence.** Producer `:155-160` creates one html string, writes it, places the same string in routes, and hashes it; server `:132-143` returns route-map content. Navigation/registration and nonce/page/input correlation support the intended fixture. However the acquisition does not retain an independently captured HTTP response-body digest or browser DOM/source digest; hash consistency authenticates retained bytes against this producer's own recorded hash, not an independent network capture. Current producer SHA-256 is `5363d576f52e72dc4e82d5838706aa307f371648e73242eed99e9776f06eceb9`, matching receipt `:4-6` and `.ufo/waves/round-21/runtime-execution-bounded.json:11-12`; that acquisition records argv, exit 0 and this row's Error stdout (`:5-18`), not a newly observed run here. Knowledge note `corpus/knowledge/webmcp-nonautosubmit-round-21.md:14-21,41` correctly separates S101 own-work from S100 source interpretation and labels this row submit-time validation after page-side mutation. No source-to-binary equivalence established. Confidence: high on these provenance boundaries.
