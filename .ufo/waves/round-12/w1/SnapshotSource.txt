## 3. Core Mechanics Breakdown

### A. Template Structure & Element Syntax
- **YAML Representation**: Accessibility tree serialized as a hierarchical YAML list where indentation encodes DOM/ARIA containment.
- **Node Signature**: `- role "name" [attribute=value]: text`
  - **Role**: ARIA or HTML semantic role (e.g. `heading`, `link`, `button`, `list`, `listitem`, `textbox`, `checkbox`). Derived from HTML semantics or explicit ARIA roles.
  - **Accessible Name**: Computed via W3C AccName computation. Exact string matching if enclosed in quotes (`"Submit"`), or regex if enclosed in slashes (`/Submit \d+/`).
  - **Attributes/States**: ARIA attributes in brackets (e.g. `[checked]`, `[disabled]`, `[expanded]`, `[level=1]`, `[pressed=true]`, `[invalid=spelling]`, `[selected]`).
  - **Text / Paragraph**: Standalone text appears as `- text: Content`; multiline blocks are normalized (`<p>A<br>B</p>` becomes `- paragraph: A B`).
  - **Link Destination**: Matchable via nested `/url` key (`- link "Doc":\n  - /url: "/intro"` or regex `- /url: /https:\/\/example.com\/.*/`).

### B. Partial Matching Mechanics
- **Attribute & Name Omission**: If an accessible name or ARIA attribute is omitted from a node, the matcher checks only the specified facets. For example:
  - `- button` matches any button regardless of text label.
  - `- checkbox` matches a checkbox regardless of checked/unchecked state.
- **Child List Subsetting**: By default (`/children: contain`), unspecified child nodes are permitted. The assertion succeeds as long as the listed nodes appear in order.

### C. Strict Matching Mechanics (`/children` Directive)
- **Control Property**: `/children` placed directly under a node modifies child matching for that specific node:
  1. `contain` (default): Requires specified children to be present in relative order; allows unlisted siblings. Empty expected children allows any children.
  2. `equal`: Requires direct children to match the template exactly in identity and order; extra unlisted direct children cause immediate failure.
  3. `deep-equal`: Enforces exact equality recursively down the entire subtree. Extra nested elements fail the match.
- **Overrides**: A nested node can declare `/children: contain` inside a parent governed by `deep-equal` to relax constraints locally.
- **Global Configuration**: `playwright.config.ts` can set `expect: { toMatchAriaSnapshot: { children: 'equal' } }` globally, overridable per-snapshot.

### D. Order Sensitivity & Scoping Limits
- **Strict Order Sensitivity**: Elements defined in the template MUST appear in the exact relative sequence found in the accessibility tree. Swapping sibling order in the template causes assertion failure even if all elements exist.
- **Single-Node Depth Scope**: A single root node in a template matches anywhere at any depth within the asserted page or locator scope.
- **Multi-Node Sibling Scope**: When a template specifies multiple top-level nodes, they MUST exist under the identical parent container in sequential order.
- **Locator Scoping**: `expect(locator).toMatchAriaSnapshot()` restricts template matching strictly to the DOM subtree of `locator`, preventing ambient page changes from affecting component assertions.
- **API Scope Control**: `locator.ariaSnapshot({ depth: N })` restricts tree traversal to `N` levels deep (added v1.59); `boxes: true` adds `[box=x,y,width,height]` (v1.60); `mode: 'ai'` emits token-efficient snapshots with `[ref=eN]` IDs and iframe traversal.

## 4. Potential Overclaims & Boundary Hazards (Inferences & Warnings)

1. **Overclaim: ARIA snapshot is pixel/visual regression testing (FALSE)**
   - *Evidence*: `playwright.dev/docs/aria-snapshots` explicitly defines ARIA snapshots as "a YAML representation of the accessibility tree".
   - *Boundary*: ARIA snapshots verify semantic structure, accessible names, roles, and ARIA attributes. They do not capture pixel rendering, canvas drawings, CSS layout shifts, colors, background styling, or font metrics. Substituting ARIA snapshots for visual regression testing is a category error.

2. **Overclaim: ARIA snapshot matching constitutes an accessibility compliance audit (FALSE)**
   - *Evidence*: S024 explicitly links to Chrome DevTools Accessibility Tab and relies on computed accessibility tree nodes, while S023 notes that semantic checks "do not replace accessibility audits and conformance tests".
   - *Boundary*: A page can match an ARIA snapshot perfectly while suffering critical WCAG failures: failing color contrast, missing focus indicators, keyboard traps, unannounced dynamic announcements, or broken landmark navigation.

3. **Overclaim: ARIA snapshots are order-insensitive (FALSE)**
   - *Evidence*: Documentation states explicitly: "The comparison is order-sensitive, meaning the order of elements in the snapshot template must match the order in the page's accessibility tree."
   - *Boundary*: Unlike bag-of-elements assertions, reordering accessible elements in the DOM will break ARIA snapshot tests unless explicitly handled.

4. **Overclaim: ARIA snapshots capture hidden or decorative DOM elements (FALSE)**
   - *Evidence*: Only accessible elements with recognized roles or text content are included in the accessibility tree.
   - *Boundary*: Elements styled with `display: none`, `visibility: hidden`, or marked `aria-hidden="true"` are pruned from the accessibility tree by browser engines and cannot be matched or asserted via ARIA snapshots.

5. **Overclaim: Multi-root templates can match elements across different parents (FALSE)**
   - *Evidence*: Documentation explicitly constrains: "Multiple top-level nodes must match under the same parent, in order."
   - *Boundary*: An author cannot list two top-level nodes in a single snapshot expecting one to match in `<header>` and one in `<footer>`; they must share the immediate parent container.

## 5. Connections to Queued Sources & Evidence Ladder (Adjacency)

- **S025 (W3C ARIA APG)**: Provides the normative specification for widget design patterns, expected roles, accessible names, and keyboard navigation contracts. It defines what the accessibility tree *should* expose.
- **S023 (Playwright Locators)**: Provides single-element actionability and semantic selection handles (`getByRole`, `getByLabel`), enforcing strictness (throwing on multiplicity).
- **S024 (Playwright ARIA Snapshots)**: Advances from single-element handles to holistic, hierarchical structural assertions over accessible subtrees. It bridges individual element queries and full page snapshots.
- **Four-Rung Evidence Ladder Integration**:
  * Rung 1 (Synthetic): Model or oral claims without browser evidence.
  * Rung 2 (Network/Transport): HTTP logs, CDP sessions, BiDi frames.
  * Rung 3 (Structural DOM / Accessibility State): ARIA snapshots and role locators belong squarely on Rung 3. They provide deterministic, structured, inspectable evidence of user-perceived state without pixel flakiness.
  * Rung 4 (Rendered Artifacts): Screenshots, video recordings, trace archives. ARIA snapshots must not be conflated with Rung 4 pixel artifacts.
