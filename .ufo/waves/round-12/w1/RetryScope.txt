2. FLAKY / PASS CLASSIFICATION INSPECTION
================================================================================
Anchor: corpus/knowledge/web-flake-retry-evidence.md:24-28, 82-88, 142-146
Source Grounding: S013 (https://playwright.dev/docs/test-retries, §Failures, §Retries)

A. Published Classification State Machine [OBSERVATION]:
- Source S013 verbatim classifies tests into exactly three outcomes:
  1. "passed" — tests that passed on the first run;
  2. "flaky" — tests that failed on the first run, but passed when retried;
  3. "failed" — tests that failed on the first run and failed all retries.
- Note reflection (:24-28, :82-84): Verbatim match to S013. A first-run pass is `passed`; a first-run failure followed by a retry pass is `flaky`; a first-run failure followed by failure across all retries is `failed`.

B. Mechanical Label Function & Incompleteness Handling [INFERENCE]:
- Note formulation (:82-87): "The label function is mechanical: all attempts pass from attempt one -> passed; first fails and any retry passes -> flaky; first fails and every configured retry fails -> failed. Missing/aborted attempt evidence -> unclassified, not an assumed pass or failure [inference from S013]."
- Note explicitly marks the `unclassified` state as an operational inference from S013's failure-and-retry definitions, preventing silent default to passed or failed when attempt records are incomplete.
- Bounded semantic attribution (:85-87): The note clarifies that `flaky` reports an observed execution sequence, not the fault's attribution (product, test, environment, or runner infrastructure).

C. Eradication of "Green After Retry" / Erasure Prohibition [OBSERVATION / REJECTED]:
- Rejection (:142-146): "A retry-pass is a reliable pass" is explicitly REJECTED.
- Core rationale (:26-28): "Thus a retry-pass is evidence of outcome variation, not evidence that the initial failure can be erased or that the underlying application is healthy."
- Receipt prerequisite (:41-43, :53-56): "A summary such as 'green after retry' is not enough to re-derive the classification... do not reconstruct a missing first failure from the final status. Apply the three labels above only when the whole configured attempt sequence is present."
- Flip condition (:145-146): Requires a version-scoped change in published runner classification and an explicit receipt format retaining all attempts.

3. ATTEMPT RECEIPT PRESERVATION INSPECTION
================================================================================
Anchor: corpus/knowledge/web-flake-retry-evidence.md:39-88
Source Grounding: S013, S014, S015, S016, S017

A. Core Contract: The Per-Test Attempt Ledger [OPERATIONAL INFERENCE]:
- Defined in §2 (:41-44): A durable ledger must track every execution from attempt 1 through attempt N (the configured retry limit).

B. Six Preserved Receipt Facets (:45-80):
1. Run Identity (:45-50):
   - Items: Source revision, exact test/project IDs, Playwright Test version, browser name/version, OS/runtime, invocation command, effective configuration, retry limit, worker/shard settings, unique run ID.
   - Lifecycle awareness (S013): Because Playwright 1.64 discards the worker process and browser on failure and starts a fresh worker for the retry, worker/attempt identity must be captured to expose lifecycle resets.
2. Attempt Outcomes (:51-56):
   - Items: First-run result, error and stack trace; for each retry: ordinal, result, error, stack, and duration.
   - Rule: Retain raw reporter output or structured equivalent; never synthesize a missing first-run failure from the final status.
3. Order Evidence (:57-62, S017):
   - Items: Whether shuffle was active, exact `--shuffle` command/seed, runner-reported seed, and observed test execution order.
   - Constraint [inference]: Replay seed must be preserved with runner version and worker/shard config; numeric seed alone is not an environment-complete replay recipe.
4. First-Retry Trace (:63-69, S014):
   - Items: `trace: 'on-first-retry'`, preserved `trace.zip`, cryptographic digest, test/attempt binding.
   - Critical preservation rule (:68-69): "Keep the first-run error separately: a retry-only trace is not the first-run trace and cannot by itself show the original failure."
5. Waited State Predicate (:70-75):
   - Items: Exact code/source revision of the predicate, target (locator/document/request), initial observed value, expected terminal value, actual observed value, timeout, pass/expire outcome.
   - Prohibition: "Waited for the page" or "slept 500 ms" is explicitly rejected as non-re-derivable.
6. Action Context (:76-81, S015, S016):
   - Items: Preceding action, locator, Playwright actionability checks/errors, assertion/matcher, and assertion timeout.
   - Boundary: Actionability checks gate action dispatch only; they do not establish post-action application state.
