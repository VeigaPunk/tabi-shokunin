## 1. Defects (ranked)

### F1 — High — The expectations file is an unbound oracle

- `check-aria-metadata.mjs:54` sets `DEFAULT_EXPECTATIONS` to the round-14 file. `:1658-1659` reads it and checks only `schema === EXPECTATIONS_SCHEMA`. Nothing compares its bytes to a digest.
- `ANCHORS` (`:62-73`) covers receipt, pin, producer, spec, config, manifest, and workers. It has no expectations entry.
- `.ufo/waves/round-14/measure.mjs` has no reference to `expected-fixtures` (grep). C2 gating (`measure.mjs:726-739`) consumes only the self-attested `selfTest.stdout` in `verification.json`.
- Consequence: the fixture pins (`fixtures.*.sha256`) and the case expectations live in the same JSON file. Editing both, together with the checker, leaves `--self-test` green and C2 green. The ReceiptRepair digest `19339f3e…` is recorded only in a prose report.

Proposed fix: add `EXPECTATIONS_SHA256` to the anchor set (or a per-file expectations anchor) and check it in `runSelfTest` before parsing, emitting `verdict=blocked` on mismatch. `measure.mjs` C2 should require `expectations.sha256` in `verification.json` to equal the committed blob.

Proposed test: copy the expectations to a mkdtemp path with one `expectedExit` flipped and assert `blocked`. The fixture-override needed for this is part of F4.

### F2 — High — Pin coverage is partial and nothing enforces completeness

- 13 fixtures are generated (`:1685-1763`). Only 8 are pinned.
- Unpinned: `sidecar-valid` (`:1741`), `sidecar-baddigest` (`:1747`), `sidecar-wrongto` (`:1752`), `sidecar-exactnode` (`:1757`), `sidecar-auto` (`:1763`). Their cases are exercised (`sidecar-valid-accepted`, `sidecar-bad-receipt-digest`, `sidecar-wrong-direction`, `sidecar-false-exact-node`, `witness-*`, `sidecar-auto-detect-check-input`), but their bytes are not pinned.
- The comparison loop at `:1765-1780` iterates only over `expectations.fixtures`. Generated-but-unpinned entries are never checked, and pinned-but-not-generated entries fail. Nothing requires `generated keys == pinned keys`.
- Consequence: a regression in `buildSidecar` or the sidecar mutations changes the bytes of five fixtures without any digest signal. Only the exit/finding outcome of their case would move.

Proposed fix: (a) fail `blocked` when `Object.keys(generated) ≠ Object.keys(expectations.fixtures)`. (b) Pin the four deterministic sidecar fixtures (see F3 for `sidecar-auto`). Values come from one clean run; L1 records them, nothing is hand-typed.

### F3 — Medium — `sidecar-auto` is not digest-stable and cannot be pinned as written

- `:1758-1763` build `autoSidecar` with `join(dir, 'receipt-old.json')` and `join(dir, 'pin.json')`. `dir` is `mkdtempSync(join(tmpdir(), 'tabi-r14-aria-metadata-'))` (`:1680`), so the random six-character suffix is embedded in the bytes. The byte length is constant but the sha256 varies per run.
- By contrast `sidecar-valid` is deterministic: `:1738-1739` pass fixed labels `fixtures/receipt-old.json` and `fixtures/pin.json`, and `buildSidecar` uses those labels (`:1165`, `:1170`).

Proposed fix: either (i) pin a normalized digest, computed after replacing the mkdtemp `dir` string with a fixed token, or (ii) make the auto-detect path relative to the sidecar's own directory so the bytes carry no tmp path. Option (ii) changes checker semantics, so MetadataEnforce should decide it. Do not pin the raw `sidecar-auto` digest.

### F4 — High — Self-test is not hermetic: fixture outcomes depend on live round-13 evidence

- `prepareContext` (`:776-781`) reads the live `DEFAULT_MANIFEST`.
- `loadWorkerContext` (`:485-592`) reads the live worker directory: `readdirSync(resolve(ROOT, WORKER_DIR))` at `:565`, the set comparison at `:573-575` (`workers:directory_set_mismatch`), and per-file reads via `readEntry` at `:524`.
- `evaluateAnchors` (`:745-749`) compares live worker bytes to `ANCHORS.workers`.
- `evaluateManifest` (`:664-690`) compares the fixture receipt's `summary.cases.expected` (`fixtureReceipt` `:1636-1642`, hard-coded `8`) with the live manifest's case count, and the live worker cases with the live manifest cases.
- The CLI child is spawned with `cwd: ROOT` (`:1795`), so every default path resolves into the live repo.
- Consequences:
  1. Clean expectations (`clean-perworker-listening`, `node-observed-recorded`, `sidecar-valid-accepted`, `sidecar-auto-detect-check-input`, and `derive-deterministic-sidecar`) turn red if a second worker file appears in `corpus/evidence/round-13/aria/actual/workers/`, or the live manifest's case count changes. Today the directory holds exactly one file (`worker-0-1530637-1792474958700.json`, sha `0d0f00e2…`), and the manifest sha is `56764241…`.
  2. Contradiction controls can pass for the wrong reason. Exit-1 cases check only the listed finding ids (see F5). A live-evidence failure that happens to fail a listed id still satisfies `old-contradiction`.
  3. The expectations description (`expected-fixtures.json:270`) says "Fixture digests bind the isolated mkdtemp bytes". That overstates isolation.

Proposed fix: inject the evidence root for the self-test only. Materialize a fixture-local `manifest.json` and `workers/` in the mkdtemp directory, byte-copied from the anchored originals (their digests are already anchored, so the copy is checkable). Pass the root to the CLI child through a self-test-only flag (for example `--evidence-root <dir>`) that the production path never sets, while the anchor digests still gate it.

Proposed tests:
- T4a: add an extra `*.json` to the fixture workers dir → expect `R14-ARIA-WORKER-SET-01` fail (exit 1) on a control case.
- T4b: alter the fixture manifest's case list → expect `R14-ARIA-MANIFEST-01` fail.
- T4c: the clean cases must stay green with the live `corpus/evidence/round-13` directory renamed. This proves the fixture-local root is the only input.

### F5 — High — The printed `finding=` is copied from the expectation, not observed

- `check-aria-metadata.mjs:1859`: `finding: testCase.expectedFindings?.[0]?.id ?? payload?.redFinding ?? 'none'`. The value comes from the expectations file.
- `:1919-1920` prints `expected_finding=${entry.finding} finding=${entry.finding}`. Both fields carry the expected id. The agreement that the measure contract enforces (`expected_finding == finding`, `measure.mjs` case-line grammar) is therefore tautological for every CLI case.
- For clean cases, `finding=` names a `pass` finding (e.g. `R14-ARIA-CLEANUP-LISTENING-AFTER-01` on `clean-perworker-listening`), so the line reports a finding that was not a failure.
- `:1890` hard-codes `finding: 'R14-ARIA-SIDECAR-ACCEPTED-01'` for `derive-deterministic-sidecar`. The derive case is also not observed.
- Exit-1 cases get no extra-fail check. The fail-set check at `:1843-1844` applies only when `expectedExit === 0`. `:1846-1852` checks only the listed ids, so an extra unexpected `fail` passes.

Proposed fix: compute `observedFail = payload.findings.filter(status==='fail').map(id).sort()`. Require exact set equality with the expected fail ids (empty for exit 0). Print `finding=` from the observed first fail id (or `none`), and keep `expected_finding=` from the expectation. The `ok` flag must include the equality. Falsifiable in-process control (no extra CLI run): feed the comparator a payload with an extra fail, and a wrong expected id; assert both produce problems.
