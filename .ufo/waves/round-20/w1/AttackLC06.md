# AttackLC06: "CancelTool uses tool-cancelled callback"

- Seat: TabiR20.AttackLC06 (leaf, author-side attack). Date 2026-10-21. Source-only: no runtime or capability claim.
- Target: `corpus/evidence/round-20/sources/html_form_element.cc:224-229` (S096). Local sha256 `8c8d6796…6916` equals `design.json` `source.sha256` and the decoded r19 copy `.ufo/waves/round-19/w1/SrcHtmlFormTool.body.gz`.
- Production edits: none. Tools installed or updated: none (`curl` and `base64` were already present).

## 1. Verdict

- The bare span is accurate. `CancelTool()` is `void` (S096:224), asserts `is_currently_running_` with a fatal `CHECK` (225), and passes `kToolCancelled` with the literal "Tool execution cancelled by abort signal" to `CallDoneCallback` (226-228).
- The intended framing is not. "Tool-cancelled callback" implies a dedicated callback, an abort cause, caller-visible delivery, and unconditional delivery. Source defeats each. Primary attack F1 is in section 2. A conditional crash path (T11) breaks the implied precondition.
- The r19 note does not hold LC06. The only r19 file that states the 224-229 claim is the wave dossier `.ufo/waves/round-19/w1/SrcHtmlFormTool.md:18`, and it says `CancelTool()` "returns" the error.

## 2. Primary attack F1

**False stronger claim.** "Aborting a running declarative tool call makes the caller receive `kToolCancelled` ("Tool execution cancelled by abort signal") through the tool-cancelled callback."

**Why the source defeats it.** Retained bodies are cited by decoded line number (`cat -n`), not registry anchors. MC = `model_context.cc` (S042 pin `474083d6…8823`). INS = `inspector_web_mcp_agent.cc` (S097 pin `1cc55ef…968475`). Both are in `.ufo/waves/round-19/w2/SourceS079.*.body.gz`.

1. **The caller never receives `kToolCancelled`.** The owner's result reaches the caller as `(string, bool)` (MC:904-921, 1179-1183). On failure the caller's promise is rejected with `DOMException` `kUnknownError` carrying the owner's text (MC:1192-1197). The code is dropped; MC:1195-1196 records this as a TODO. The text comes from `GetToolErrorMessage()`, which returns `error.message` when non-empty (MC:183-186). Net: a non-aborting caller sees an UnknownError whose message is the S096 literal. [INFERENCE on the browser transport; only the reply shape is retained.]
2. **An aborting caller sees its own reason first.** The abort algorithm rejects with `signal->reason()` (MC:1155-1158), then relays `CancelRemoteScriptTool` (MC:1159-1162).
3. **The literal names an abort the path never performs.** The declarative branch only calls `DeclarativeTool()->CancelTool()`, then `CHECK(!pending_executions_.Contains(...))` (MC:612-619). It never aborts the owner's controller. The imperative branch does (MC:630-635). The form tool receives no controller: `ExecuteTool(invocation_id, input_arguments, done_callback)` (S096:174-177).
4. **The same literal occurs with no AbortSignal at all.** CDP `cancelInvocation` calls `ModelContext::CancelTool` (INS:139-165, call at 152), which reaches the same declarative branch.
5. **`kToolCancelled` is not an abort marker.** S096 also raises it at 391-394 (form no longer a valid tool), 449-451 (replaced definition) and 1102-1104 (form reset). Those sites use different messages and call `CallDoneCallback` directly. These lines are outside the registered S096 anchors; see section 4.
6. **S096 shows no trigger.** `CancelTool` appears once in the file (224). The span cannot show what calls it.

**Acceptable wording.**

- Minimal manifest row LC06 (S096 span only):
  - condition: `CancelTool()` runs while the invocation is running, that is after `is_currently_running_` is set at line 204. A cancel before that point violates the `CHECK` at line 225 (see T11).
  - outcome: `CancelTool()` is void. It passes `kToolCancelled` with the fixed text "Tool execution cancelled by abort signal" to `CallDoneCallback()`, which runs the pending done callback. Delivery and state clearing are LC07 (261-275). The span shows no caller and no abort.
  - startLine 224, endLine 229, quote `Tool execution cancelled by abort signal` (line 228; 6 whitespace words; single-line literal).
- Knowledge-note sentence (cross-source, source-level only; the S096 lines outside anchors need registration first):
  > On the declarative path, `HTMLFormMcpTool::CancelTool()` (S096:224-229) gives a running call the error `kToolCancelled` with the fixed text "Tool execution cancelled by abort signal". That text does not report an abort: the declarative branch fires no AbortSignal (model_context.cc:612-619); CDP `cancelInvocation` reaches the same method (inspector_web_mcp_agent.cc:152); and `kToolCancelled` is also raised on form invalidation (S096:391-394), definition replacement (S096:449-451) and form reset (S096:1102-1104). A non-aborting `executeTool` caller sees an UnknownError carrying the owner's text (model_context.cc:1190-1197); an aborting caller sees its own abort reason first (model_context.cc:1157). No runtime observation.

## 3. Secondary traps

- **T1. "CancelTool always delivers kToolCancelled" / "is a no-op when nothing runs."** Method level: `CHECK(is_currently_running_)` is fatal in every build (S096:225; upstream `base/check.h` at tag 154.0.8037.97, lines 22-24 and 244-275, fetched this session). Entry level: `ModelContext::CancelTool` returns false when no execution is pending (MC:588-591), and CDP then returns InvalidParams "No pending execution for invocation id" (INS:159-161). That pending test does not establish running (T11). `CHECK(document_->IsActive())` (MC:583) is a separate precondition. Wording: "CancelTool() requires a running invocation (fatal CHECK otherwise). A cancel for an id with no pending execution returns false before the method runs (MC:588-591)."
- **T2. "tool-cancelled callback."** Not a separate callback. S096 runs the done callback stored at line 210, which is the ModelContext lambda (MC:719-745). The page-visible `toolcancel` event is different; it is dispatched after the cancel branch (MC:643-647). Wording: "the pending done callback (done_callback_, S096:210)". Never "tool-cancelled callback".
- **T3. "CancelTool returns kToolCancelled."** It is `void` (S096:224). The r19 dossier (`.ufo/waves/round-19/w1/SrcHtmlFormTool.md:18`) uses "returns"; that verb is wrong. Wording: "CancelTool() delivers kToolCancelled through CallDoneCallback()".
- **T4. "The tool is no longer running when the cancel callback runs."** The callback runs first (S096:266), then `is_currently_running_ = false` (267), then invocation id and pseudo-state are cleared (268-273). The CDP probe runs inside the callback (MC:736-737), when `CurrentlyRunning()` is still true. Wording: "CallDoneCallback runs the callback before clearing running state (S096:266-267)."
- **T5. "CancelTool is the only cancellation path."** Three other sites call `CallDoneCallback` directly with kToolCancelled (S096:391-394, 449-451, 1102-1104). Only 390 and 448 test `IsHandlingSubmit()`. CancelTool (224-229) and reset (1101-1105) do not. Wording: "CancelTool is one of four kToolCancelled sites."
- **T6. "A cancel defers to an in-flight submit."** No such guard in CancelTool or reset; the guard appears only at 390 and 448. Whether a cancel can interleave with submit dispatch (for example through a nested event loop) is not shown in S096. [INFERENCE] Wording: state the guard difference only; do not claim deferral.
- **T7. "The executeTool caller gets kToolCancelled."** See F1 point 1. Wording: "A non-aborting caller gets DOMException UnknownError with the owner's text; an aborting caller gets its abort reason."
- **T8. "Declarative cancel is observed as status Canceled with errorText."** Source only. INS:228-230 maps kToolCancelled to Canceled; INS:241-243 forwards `error.message`. The only runtime Canceled in the tree (r17 note row 62, `invoke-cancel`) has `errorText ""`, which matches the imperative branch's empty message (MC:639-640), not the declarative literal [INFERENCE on tool kind]. The page-side-abort case was "not re-run" (r17 note line 97). Wording: "Source predicts toolResponded status Canceled with errorText equal to the S096 literal for a declarative cancel. Not runtime-observed; r19 has no cancel case."
- **T9. "Unregistration cancels pending calls"** (generalized from r17). The r17 probe `invoke-unregister-while-pending` covers registerTool (imperative) tools and found no cancel (r17 note row 74; not a receipt case). Declarative invalidation does cancel (S096:390-394) unless handling submit. Neither result carries over. Wording: "For registerTool tools, the r17 probe saw no cancel on unregistration. For declarative forms, invalidation calls CallDoneCallback with kToolCancelled unless handling submit (S096:390-394)."
- **T10. "Cancelling returns a paused agent to normal execution."** `PauseExecution()` is set for user-gated tools (S096:217). No resume appears in S096 or in the retained S042/S097 bodies (checked). The release path is not retained. Wording: "CancelTool does not show a release of PauseExecution; the release path is not in the retained sources."
- **T11. "CHECK(is_currently_running_) at 225 is unreachable, because ModelContext only cancels running invocations."** Pending is inserted before the fill (MC:712-717), and `ExecuteTool` then runs the fill (MC:719; S096:189-194). The running flag is set only after the fill (S096:204). So while page script runs inside the fill (S096:178-203), a cancel finds a pending execution, and the CHECK at 225 fails: fatal. Reaching this needs a cancel processed during synchronous page events inside the fill, which needs a nested event loop. Not established in-tree. [INFERENCE] Wording: "A cancel is valid only after the fill completes and the running flag is set (S096:204). The ModelContext pending check does not establish that."
