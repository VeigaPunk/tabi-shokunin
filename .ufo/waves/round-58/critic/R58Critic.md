## C1(a) — can hand-edited `-r58` ledger rows green the meter? Partially; the meter cannot see provenance

**What the head/sha cells detect (from `verify()`, P3).** The meter reads the ledgers **at `--rev` through git** (`laneBytes(repo, rev, DELTA_REL)` — only committed ledger edits are ever visible), takes **its own per-run head snapshot** (`headSnapshots()` at meter start), and re-derives every lane-row cell from those snapshot-head bytes (`makeSibRefGit` → `git cat-file -p <head>:<path>`; the worktree is never read). Detection ids, each with its cell:

| cell | re-derivation | finding id |
|---|---|---|
| `head` | vs the meter's run-time snapshot head (`headOf`) | `lane-screen-head-mismatch` |
| `provinceSha256` | sha256 of the province bytes at the snapshot head | `lane-screen-sha-mismatch` |
| `lines`, `bgHits` | line count / BG-keyword hit count re-derived from the same bytes | `lane-screen-lines-mismatch`, `lane-screen-hits-mismatch` |
| `line` rows | exact whole-line quote + frozen-vocabulary disposition per derived hit; invented line rows flagged | `delta-line-missing`, `delta-quote-not-whole-line`, `delta-disposition`, `delta-line-invented` |

**What slips through.** Nothing in the pure core binds the ledger rows to the **committed rebind snapshot** — `adj/rebind-snapshot.json` is not a meter input (CLI is `--rev/--repo/--fleet` only). Consequence, concrete: for a **bytes-unchanged head movement** (kengaku's signature move — verified: `PROVINCE.md` sha256 `f0b82513…bba736` and 971 lines identical at `21b13dc7`, `12a62551`, and live `b5032ff8`), a hand-edit of **only the `head` cell** to the moved head makes every re-derivation agree, and the meter goes green. The meter cannot distinguish "re-derived at a fresh snapshot" from "head cell hand-copied to the run-time head". Two adjacent observations from the same code read: (1) a sibling_ref's embedded `<rev>` is **documentary only** — `verify()` re-derives audit status via `sibRef(lane, path)` at the run-time head and never compares the ref's rev to anything, so editing that cell is undetected (and changes nothing measured); (2) if the sibling's head is unresolvable at run time (`rev-parse` fails → `headOf` null), the head check is skipped and an all-`-` lane row silently passes P3 while P2 still counts it as coverage — contrived (needs a broken sibling repo) but real.

**What constrains the attack (detection is post-hoc, not in-instrument).** (1) The kill rule itself: "the only path to green is editing a ledger row to match bytes not at the rebind snapshot head" is fatal to the claim. (2) The receipt prints `headSnapshot` per lane, so any auditor can compare the committed receipt's run-time heads against `adj/rebind-snapshot.json` and the ledger file's own git history (the edit must be a commit at the data revision). (3) If province bytes DO change with the movement, editing `head` alone stays red (sha/lines/quote findings); greening then requires recomputing cells from the moved head's bytes — exactly the kill rule's words. Also note the edit is only coincidentally stable: a further sibling move re-reds the meter.

**Smallest safe correction.** Nothing may go into v18 — the frozen declared change set is (a)/(b)/(c) only, and a post-freeze predicate change is a new claim. Route forward: the **v19 generation's `runAt()` should read `adj/rebind-snapshot.json` and emit `rebind-snapshot-head-mismatch` when any ledger `head` cell ≠ that lane's committed snapshot head** — this converts the post-hoc audit into an in-instrument refusal and closes the bytes-unchanged slip-through. Operationally now: the L1 should run the v18 meter immediately after the rebind commit (minimize the freeze→data window) — kengaku moved twice on 2026-11-03 alone (16:50:37, 17:04:37) and has been the mover in every round-open red since r53 (named in the v17 header for r53/r54/r55/r56 and in this round's control receipt).

## C1(c) — can harness-guard pass while the harness still lies?

**The v17 selftest case list (18, carried unchanged into v18):** honest-green, audit-missing, status-mismatch-moved, stale-misclaimed, moved-claimed-honestly-green, moved-note-wrong-line, file-absent-at-head-honest-green, file-absent-misclaimed, roster-lane-uncovered, delta-quote-spliced, lane-screen-sha-mismatch, lane-screen-hits-mismatch, delta-line-missing, delta-line-invented, audit-duplicate, lane-screen-head-mismatch, predicate-assert-green, predicate-assert-partial. v18 adds `map-ref-unparseable` + `harness-guard` → 20, matching the claim.

**The mutant in question (fix `caseOk`, mutate the run loop's own emission `predicateFrom`).** In the v17 harness the run loop computes `const emitted = predicateFrom(findings)` and `okPredicate` compares `emitted` to the case's `assertPredicate`. A `predicateFrom` mutation is caught **by the two carried predicate-assert cases, not by harness-guard**: AND→OR (`findings.length !== 0`) makes green emit `false` against `assertPredicate: true` (fail) and partial emit `true` against `assertPredicate: false` (fail). So yes — that combination is caught, by carried cases. Equivalent mutants of `predicateFrom` (e.g. `findings.length <= 0`) survive both asserts but are observationally equivalent (length ∈ ℕ) — harmless.

**The named residual.** `harness-guard` protects only the **named** `caseOk` function's truth table. If the (c) refactor is not honored as a real extraction — the run loop keeps a **duplicated inline conjunction** (`ok = okFindings && okPredicate && okCount`) while the named function sits unused — an mG-class mutant applied to the inline conjunction leaves the selftest green: `harness-guard` tests the intact, unused function and passes. **No selftest case catches that.** The only catch is the diff discipline: the duplicated conjunction appears as differing lines outside (a)/(b)/(c) in `counters/v17-v18-meter.diff` / `adj/v18-line-audit.txt`. **The line audit is therefore load-bearing, not ceremony**: it must explicitly account the run loop's verdict line as a `caseOk(...)` call site (single call site = the extraction is real). I recommend the L1/reviewer check exactly that line in the audit file.

## C2(a) — is the swallow design causally sound? Yes; each named hazard is ruled out by design

- **IME:** ruled out by the injection path. CDP `Input.dispatchKeyEvent` injects raw key events with no IME session (throwaway profile, no input method enabled); digits/Backspace/Enter on a plain `<input>` produce no composition. A composition-adjacent state would surface as keyCode-229 keydowns that fail the counter's per-leg key/cancelable checks (`k1`–`k3` require the real key names with `cancelable true`) — refused, not false-green.
- **Repeating keys:** ruled out by the dispatch shape — each swallow-leg keystroke is a single driver dispatch from the frozen declared step list, and the counter re-derives the expected keylog plan from the receipt's own nonce (one entry per keystroke). Auto-repeat cannot arise from single dispatches, and per-event `preventDefault()` would cancel repeats anyway.
- **Read-only field:** ruled out **in-run** — leg s1 (control, swallow OFF) types the two nonce digits into the *same* `#field3` immediately before the swallow legs and requires `valueAfter ==` them. A read-only, disabled, or unfocused field fails s1 before any swallow claim is made.
- **Cancelable ground:** the recorder takes `cancelable` from the event and every swallow check requires `cancelable true`; UI Events (S161, re-opened) makes keydown cancelable for these keys and specifies that canceling keydown prevents the default action (the insertion), which Chromium honors for plain inputs (canceled keydown ⇒ no beforeinput/insertion). The design refuses a non-cancelable delivery instead of passing it.

## C2(b) — listener order: holds; the operative guarantee is registration order, and a mis-phased build cannot green

The guarantee carrier in the R58Runner item is the FIXTURE sentence — *"add a capture-phase SWALLOWER listener registered BEFORE the r57 recorder"* — together with the recorder delta — *"defaultPrevented (the event's flag AFTER the swallower ran - capture order guarantees it)"*. Ground truth from the r57 driver bytes: the recorders are **capture-phase listeners on `document`** (`document.addEventListener('keydown', rec, true)` for `__keylogFull`, lines ~518–519; the r56 `__keylog` keydown-only recorder is also document-capture, ~line 496). For same-node listeners the DOM dispatches in **registration order regardless of capture flag**; the capture designation additionally puts the swallower ahead of any non-document (target/bubble) listener. So "registered BEFORE" is the load-bearing half; "capture order" is an imprecise but effect-equivalent shorthand for the same outcome.

Counterfactual: if the built fixture registers the swallower **bubble-phase** on document (or on `#field3`), the capture recorders read `defaultPrevented = false` — while the value witness would still pass (a bubble-phase `preventDefault()` still cancels the insertion default). Result: legs s2/s3 record `defaultPrevented false` and counter checks `k2`/`k3` emit `swallow-defaultprevented-missing`. A mis-phased fixture **cannot green** — precisely the delivered-but-swallowed vs acted-on distinction the two recorded fields exist to make.

## Defect flags for the L1 (nothing here amends the frozen text)

- **D1 — fixture-wording hazard (frozen-text ambiguity, binding side is the assertion).** Both claims.json C1(b) and the dispatch describe the `map-ref-unparseable` fixture as "an **audit row** keyed by a ref with a malformed line-number suffix". In `verify()` bytes, `map-ref-unparseable` is emitted **only from a MAP row's unparseable `sibling_ref`**; an audit-row-only malformed key yields `audit-missing` (or nothing) and the case would fail under the *honest* v18. The fixture must carry the malformed suffix (e.g. `<lane>@<rev>:<path>:12x`) on the **map row's ref**; the audit row keyed by the same string is then inert (P1 `continue`s before the audit lookup). The assertion side holds as specified: under the `/^\d+$/` → `/^\d+/` weakening the ref parses as line 12, the id disappears, and the case fails via its declared ids regardless of claimed status (a zero-finding mutant also fails because `ids` is declared — note an `expect>0` case **without** `ids` vacuously passes `okFindings` via `every()` over `[]`; both new cases must keep ids declared).
