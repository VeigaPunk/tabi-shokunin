IMPLICATIONS FOR THE NOTE'S Limits SECTION (counter scripts/check-filechooser-r78.mjs)
1. The activation-law ("a chooser event is bound iff the click that reached a file input carried transient activation while interception was on", check-filechooser-r78.mjs:505-507) is NOT attackable via showPicker: without activation showPicker throws before any protocol event (S1/S2), so it cannot forge a chooser event where the law expects none.
2. But showPicker IS a second, click-free OPENING path when activation exists (S3): the chooser event is byte-identical in shape to a click-opened one, and the page-side trusted pointer sequence on the input is absent. A receipt binding "chooser event → click on the input" would be wrong for a showPicker producer; the r78 counter's legs avoid this only because its send-log allow-list is closed: any Runtime.evaluate outside EXPRS is refused (check-filechooser-r78.mjs:435, 441 — the allow-list contains no showPicker expression), so an unplanned showPicker evaluate fails chooser-send-shape regardless of events.
3. The sharper edge is S6: CDP userGesture:true alone opens the chooser with no page activation and no input events. The producer's own look-alike detector does flag userGesture===true evaluates (scripts/chrome-cdp-filechooser-round78.mjs:468-469), but its expression regex (`/\.click\(|dispatchEvent|\.files\s*=|DataTransfer|__events\.push|__stub/`, :469) does NOT contain `.showPicker(` — a future counter that trusted expression-matching instead of the userGesture flag would miss this path. The durable defense is the closed EXPRS allow-list, not event- or expression-matching.
4. Counter-fact for any page-activation-based reasoning: transient activation is CONSUMED by an intercepted chooser open (S5 shows isActive=false right after the click-opened chooser; the driver's own leg shapes show act=false on every input/change/cancel event after the click). A chooser counter must read activation DURING the click event, as the fixture recorder does — never after.
