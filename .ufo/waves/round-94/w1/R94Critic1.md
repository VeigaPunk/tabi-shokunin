## Answers to the three especially-checked questions

1. **Is "every backendNodeId in the pierced tree is < B" fully implied by `maxBackendNodeId < B`?** In logic, `max < B` ⊢ every < B — **but only if the `max` field is the true maximum.** The counter trusts the driver's scalar (`ppOk` = integer check only); it never sees the node list, and it ignores `nodes`. Under `--live` with the pinned driver, `treeStats` walks the same `DOM.getDocument{depth:-1,pierce:true}` tree the words name, so max<B is faithful here. In `--receipt` mode the implication collapses (pigeonhole/negative-max forgeries above all score clean). This is a counter weakness by design — declared limit 6 explicitly disclaims receipt-mode forgeries ("a forger who writes a whole consistent receipt passes that mode; the claim's counting command is `--live`"). Not a falsifies-wording case: I found **no** `--live` (or otherwise in-scope) run where the pinned driver's max under-reports while describing a real tree. The fixture has no `<template>` to break the walk.
2. **Is "painted" spans enforced?** Not by the counter at all (no span data in any receipt field — M/C pierce counts the *parent* tree). Under `--live` it is fixed by the pinned driver bytes (spans rendered visible by construction) *and* by the outcome: with hidden spans the M arm collapses to B=2 collision and the frozen counter flags it (peer Critic2 variant d is this counterexample). Receipt forgery `R94Critic1-e-*.json` passes rc 0 — limit 6.
3. **Is the 1500 ms window enforced?** Not in the receipt (no timing field; counter checks one chooser exists). Under `--live` the driver bounds the scan to a fixed 1500 ms sleep after the click and then reads only events already arrived, so a >1500 ms chooser leaves zero choosers and the counter fails. The window is enforced by the scan mechanics, not by measurement. Forgery `R94Critic1-f-*.json` passes rc 0 — limit 6.
