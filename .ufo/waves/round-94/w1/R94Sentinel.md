## 6. Trust-boundary findings

**F1 (HIGH) — the `--live` evidence channel is not tamper-evident; `--live` is no stronger than `--receipt`.** Declared limit 6 concedes that a forger writing a whole consistent receipt passes `--receipt` mode and relies on `--live` being the sound mode. It is not. The counter mints the nonce and passes it to the driver **on the command line**; the driver writes the receipt to a *predictable* path `<S>/live-receipt.json`; the counter reads that path **after** the driver exits. A same-UID writer can (a) read the nonce from `/proc/<pid>/cmdline` (demonstrated: learned `tabi-r94-live-f18ca427a569`, matched the counter's) and (b) overwrite the receipt in the window between the driver's write and the counter's read. Demonstrated end-to-end: my substituted file was certified **`verdict: clean`, 165 checks, 0 findings**, with the counter's `receiptSha256` equal to my file's hash — the counter certified bytes the pinned driver never produced. (A forged receipt *pre-planted* before the run is correctly overwritten — `R94Sentinel-receipt-mode.json` shows that benign case — so the exploit needs the post-write race, which I reproduced with a concurrent writer.) A forger who fabricates a self-consistent receipt asserting the claim while the browser actually violated it would obtain a clean verdict. **Remediation:** have the driver write the receipt to a mode-0600 file in a directory it creates itself, and have the counter verify inode/device + mtime; or have the driver emit the receipt on a pipe the counter reads; or pass a per-run secret by an inherited fd (never argv).

**F2 (MEDIUM) — a host-resource failure is reported as `findings` (rc 1), making a *true* claim look false.** When chromium cannot launch — e.g. `TMPDIR` ≥ 63 bytes, so chromium's AF_UNIX singleton socket exceeds the 108-byte `sun_path` limit and it dies `FATAL: process_singleton_posix.cc: Socket path too long` (threshold measured: 62 bytes OK, 63 fail) — every leg records `devtools endpoint never answered` and the counter reports `verdict: findings`, rc 1, **165 checks and 107 findings**, whose id set overlaps a genuine falsification on 6 ids (answer, child-files, describe-chooser, describe-page, page-pierce, page-root). A consumer mapping exit 1 to "the claim is falsified" is misled; the plan's kill rule requires host-resource failures to be *named as such*. Artifacts `R94Sentinel-launch-failure-longtmp.json` + `-launch-failure-longtmp-receipt.json`. **Remediation:** the driver should distinguish "chromium failed to start" from "leg errored" and exit 2; the counter should map a run in which every leg failed identically before any observation to `setup`.

**F3 (LOW) — the counter's own-signal refusal omits `driverRun` and `revision`.** On SIGINT/SIGTERM/SIGHUP the `refuse()` call passes no extras, so the setup JSON has no `driverRun` (hence no machine-readable `orphansSwept`) and no `revision` (`R94Sentinel-setup-counter-{sigterm,sigint,sighup}.json`). The frozen control artifact has the same shape, so this is committed behaviour, not a regression — but the sweep count survives only inside the human-readable `detail` string.

**F4 (MEDIUM) — a pre-existing directory at the receipt path crashes the counter with no verdict.** The counter does `fs.rmSync(receiptPath, { force: true })`; with a *directory* there node throws `ERR_FS_EISDIR` uncaught: rc 1, stdout empty (`R94Sentinel-receipt-path-directory.json`, 0 bytes). Exit 1 means "findings" in the counter's own contract, so a consumer can read a crash as a falsification. **Remediation:** wrap the setup in try/catch and emit `verdict: setup`.

**F5 (MEDIUM) — the frozen counting command as written writes under `/tmp`** (see §3): no `TMPDIR` in `plans/round-94.md` §Counting command, and the driver does not override chromium's environment, so 9 `/tmp/org.chromium.Chromium.*` dirs are created per 9-leg run, violating the wave contract's "never write under /tmp" for whoever executes it. **Remediation:** the driver should point chromium's `TMPDIR` (and `HOME`/`XDG_CONFIG_HOME`) inside `--scratch`, as `scripts/check-bidi-runtime.mjs` does.

## 7. Disclosure — collateral damage I caused

My first driver-SIGKILL control used `pgrep -f "chrome-cdp-backendnode-collision-round94.mjs --lane $LANE"`, a pattern matching **every seat's** driver because all seats share the lane path, and `head -1` took the lowest PID. I SIGKILLed pid 890786, which was **R94Exec2's run3 attempt-1 driver**, not mine (mine completed normally: 9 legs, `failures: []`). That is why R94Exec2's summary records "first attempt RC 2 verdict=setup detail='driver ended by signal SIGKILL' orphansSwept=14; retry on same ports RC 0 clean (resource/setup transient)" — their first attempt failed because of my mis-targeted pattern, not host pressure. Their **cited artifacts come from the successful retry and are unaffected** (R94Exec2-run3.json / -run3-receipt.json: clean, 165 checks, 0 findings, 9 legs). I re-ran the control matching only my own scratch path (`pgrep -f -- "--scratch $SC/driver"`); the corrected control reproduces the frozen verdict (`R94Sentinel-setup-driver-sigkill.json`), and the mis-targeted attempt is kept verbatim as `R94Sentinel-mistargeted-attempt.json`. No peer artifact was corrupted: all peer counter JSONs still parse as `clean`/165/0 and every peer receipt still has 9 legs and `failures: []`. Lesson for the lane: on a shared host with a shared lane path, **never `pkill -f`/`pgrep -f` by script name** — match on the seat's own scratch path or port.
