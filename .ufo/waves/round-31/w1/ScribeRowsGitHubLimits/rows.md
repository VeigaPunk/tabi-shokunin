# C1 row draft — S121 (GitHub REST API rate limits)

Seat: ScribeRowsGitHubLimits · source row: S121 · url: https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api
Scope label for every row below: **vendor policy for one host's REST API** (api.github.com as documented on docs.github.com). Nothing here describes a limit on fetching the documentation pages themselves, and none of it is a runtime measurement.

Rows (table body only — the frozen header `| Row | Signal | Decision | Threshold | Source | Located quote |` is written by the L1):

| D1 | secondary-limit `403` or `429` with no `retry-after` and `x-ratelimit-remaining` not `0` | wait at least one minute before retrying (vendor policy: GitHub REST API, last-resort branch of the secondary-limit remedy) | at least 1 minute | S121 | "Otherwise, wait for at least one minute before retrying." |
| D2 | `x-ratelimit-limit` reads 60 on an unauthenticated request | cap pacing at 60 requests per hour (vendor policy: GitHub REST API, unauthenticated) | 60 requests | S121 | "The primary rate limit for unauthenticated requests is 60 requests per hour." |
| D3 | `x-ratelimit-limit` reads 5000 with a personal access token | cap pacing at 5,000 requests per hour (vendor policy: GitHub REST API, personal token) | 5,000 requests | S121 | "All of these requests count towards your personal rate limit of 5,000 requests per hour." |
| D4 | `x-ratelimit-limit` with an installation access token | cap assumptions at the installation minimum of 5,000 requests per hour (vendor policy: GitHub App installations) | 5,000 requests | S121 | "GitHub Apps authenticating with an installation access token use the installation's minimum rate limit of 5,000 requests per hour." |
| D5 | `x-ratelimit-limit` reads 1000 under `GITHUB_TOKEN` | cap pacing at 1,000 requests per hour per repository (vendor policy: GitHub Actions `GITHUB_TOKEN`) | 1,000 requests | S121 | "The rate limit for GITHUB_TOKEN is 1,000 requests per hour per repository." |
| D6 | `x-ratelimit-limit` above 12500 on a non-Enterprise installation | cap the scaled installation budget at 12,500 requests per hour (vendor policy: GitHub REST API, non-Enterprise Cloud installations) | at most 12,500 requests | S121 | "The rate limit cannot increase beyond 12,500 requests per hour." |
| D7 | parallel fan-out to one host (`concurrent requests`) | cap concurrent requests at 100 (vendor policy: GitHub secondary limit, shared across REST and GraphQL) | no more than 100 concurrent | S121 | "No more than 100 concurrent requests are allowed." |
| D8 | weighted `points` burst on one REST endpoint | cap weighted points at 900 per minute (vendor policy: GitHub secondary point limit, REST endpoints) | no more than 900 points | S121 | "No more than 900 points per minute are allowed for REST API endpoints" |
| D9 | summed `CPU time` proxy (total response time) over 60 s of wall clock | cap estimated CPU time at 90 seconds per 60 seconds (vendor policy: GitHub secondary compute limit) | no more than 90 seconds | S121 | "No more than 90 seconds of CPU time per 60 seconds of real time is allowed." |
| D10 | content-creating `POST` `PATCH` `DELETE` calls | cap content-generating requests at 80 per minute (vendor policy, general case: some endpoints have lower limits) | no more than 80 requests | S121 | "In general, no more than 80 content-generating requests per minute" |
| D11 | `OAuth access token` request burst | cap OAuth access token requests at 2,000 per hour (vendor policy: GitHub Apps and OAuth apps) | no more than 2,000 requests | S121 | "No more than 2,000 OAuth access token requests per hour are allowed for GitHub Apps and OAuth apps." |
| D12 | Git LFS batch request `429` | cap the LFS bucket at 300 requests per minute unauthenticated (vendor policy: separate LFS bucket) | 300 requests | S121 | "a limit of 300 requests per minute for unauthenticated requests and 3,000 requests per minute for authenticated requests" |

## Why each decision follows from its quote

- **D1** — The quote is GitHub's own remedy for the branch that is neither `retry-after` nor `x-ratelimit-remaining: 0`: it fixes a floor of one minute before the next attempt. Strength: advisory "wait" (a recommendation, not a MUST); scope: GitHub REST API secondary limits. The signal cell only names the branch the quote sits in.
- **D2** — The quote states the unauthenticated ceiling as a fact of that host's policy, so a driver without credentials can plan its pace only up to 60 requests per hour. Strength: declarative vendor policy (no RFC 2119 keyword); scope: GitHub REST API, unauthenticated, per originating IP.
- **D3** — The quote attributes a 5,000 requests-per-hour budget to the personal access token itself, so authenticating with a token does not remove the bound — it sets it. Strength: declarative vendor policy; scope: GitHub REST API authenticated as a user.
- **D4** — The quote names 5,000 requests per hour as the *minimum* an installation token carries, so 5,000 is the floor to plan against, not a ceiling. Strength: declarative vendor policy; scope: GitHub App installation tokens.
- **D5** — The quote fixes the Actions `GITHUB_TOKEN` budget per repository, so a workflow driver must cap per repository, not per workflow run. Strength: declarative vendor policy; scope: GitHub Actions `GITHUB_TOKEN`.
- **D6** — The quote is a stated ceiling on the scaled installation budget, so planning above 12,500 requests per hour is planning for a rate the source says cannot occur. Strength: declarative vendor policy; scope: installations outside GitHub Enterprise Cloud (the 15,000 rows apply inside it).
- **D7** — The quote bounds concurrency numerically and separately from request counts, so a driver that fans out in parallel must cap in-flight requests, not just total requests. Strength: declarative vendor policy ("are allowed"); scope: secondary limit shared across REST and GraphQL.
- **D8** — The quote bounds weighted points per minute for REST endpoints; the page's point table (GET/HEAD/OPTIONS cost 1, writes cost 5) makes the bound reachable by a few writes, so the decision is to cap the weighted rate. Strength: declarative vendor policy; scope: REST API endpoints (GraphQL has a separate 2,000 bound).
- **D9** — The quote bounds CPU seconds per 60 seconds of real time and the page says CPU time can be estimated from total response time, so the driver caps its summed response time per minute. Strength: declarative vendor policy; scope: secondary compute limit, REST plus GraphQL.
- **D10** — The quote bounds content-generating requests per minute and marks the bound as the general case, so the decision carries that caveat rather than claiming a universal cap. Strength: declarative vendor policy with an explicit "in general"; scope: content creation via API and web interface.
- **D11** — The quote bounds OAuth access-token requests per hour for both app kinds, so a driver that refreshes tokens in a loop must pace them separately from ordinary calls. Strength: declarative vendor policy; scope: GitHub Apps and OAuth apps.
- **D12** — The quote gives the Git LFS bucket its own per-minute allowance, separate from the primary budget, so LFS traffic must be capped against that bucket. Strength: declarative vendor policy; scope: Git LFS access API, unauthenticated (3,000 for authenticated).
