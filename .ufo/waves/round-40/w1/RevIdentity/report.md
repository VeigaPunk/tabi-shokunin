## Ownership semantics

- The driver starts Firefox through `firefox.launch()`. After a 400 ms delay, it captures a process table using `ps -eo pid=,ppid=,args= --no-headers`; `ownedRoots(process.pid)` selects processes whose immediate PPID is this driver Node PID and whose args contain a path matching `ms-playwright/firefox-<digits>/`. It records each selected PID and `argv0`; `rec.binary` is the first root's argv0 (fallback constant only if no root).
- It then takes one descendant-tree snapshot via a second `ps` table and PPID breadth-first traversal from the roots. Receipt fields `owned.nodePid`, `owned.roots`, `owned.tree`, and `owned.source` describe that relation. The `owned.tree` nonempty check is scored by the counter. This ties the observed process set to the driver's process ancestry and executable-argument pattern at that observation; it is not a cryptographic/process-handle identity proof.
- The tree is **not refreshed over time**. The same `rec.owned.tree` PID array is used for every periodic `sampleSockets` call and the final post-close sweep. Thus newly spawned descendants after the initial snapshot, or children no longer reachable by the sampled PPID walk, are not added. Per-PID `/proc/<pid>/fd` enumeration failures are skipped as exited; the whole proc surface can still report `ticks:1` with no inodes if all such PIDs disappeared. A PID that exits and is reused during the run is not guarded by a start-time/`pidfd` identity check. These are limits of what the evidence establishes, not claims that a mismatch occurred.

## Tracking and scored observables

- The sampler interval is 100 ms. Each sample records `t: Date.now()` and `ss`/`proc` observations over the static tree. `ss` runs `ss -Htnp` and filters output for owned PIDs; proc matches socket inode symlinks under each tracked PID's fd directory against `/proc/net/tcp` and `tcp6`. A final sweep calls the same two observers after browser close and a 600 ms tail. Counter v3 checks >=8 samples, strictly increasing `t`, end-minus-start >=1000 ms; both surfaces usable with positive `ticks` and zero `nonLoopback` for each sample and final sweep.
- `ticks` is set to 1 when that observation routine succeeds; it signals a successful routine/read, not an independently audited count of OS sampling events. `ss` tick can be positive with zero matching lines. Proc tick can be positive with zero matching inodes. The counter requires this tick, not positive socket count.
- Cleanup evidence is `survivorPids`/`survivors` from existence checks on the initial tree PIDs, plus `portClosed` from `ss -Hlt` not containing the fixture port. Counter requires the empty survivor list, count zero, and `portClosed===true`. These are observations at the cleanup check, not guarantees about later process/port state.

## Nonce, version, and descriptive/self-reported fields

- The measurement wrapper generates 32 random bytes as lowercase hex, passes the nonce to the driver with `--round40 --runs 2`, reads the newly written output, requires receipt/run `runNonce` equality, then passes the same nonce to the counter. It rejects an output path already existing before launch. Driver round-40 argument validation requires exactly two runs and a 64-hex nonce; receipt carries it at top level and each `runOnce` record. This establishes wrapper/receipt nonce agreement at the source level; the nonce is not a process-session authentication credential, and no claim of session authentication is made.
- `browserVersion` is taken from Playwright's `browser.version()` after launch and the counter requires a nonempty string in each run. `userAgent`, `binary`, `owned.source`, `measuredAt`, browser events/commands, `coverageMs`, `sampleCount`, summary socket totals, and `binding` are receipt-produced descriptive fields; counter v3 does not independently validate most of them. Specifically it validates first-shot hash shape/equality and per-run version presence, but does not verify userAgent against the binary/version, nor inspect actual screenshot bytes against the supplied hash.
- Non-loopback counts, timestamps, ticks, PID tree, survivor observations, port-closure flag, nonce fields, and version are generated and then serialized by the same driver; the counter validates their structure/values from the receipt, not by independently re-running OS observations. Wrapper's `driverSha256` and captured process exit/stdout/stderr are wrapper output, but the counter scores the receipt only. Therefore the counted run has live driver invocation/provenance binding per wrapper logic; individual receipt assertions remain observations emitted by that code rather than independently authenticated kernel evidence.

## Finding / calibration

The fields that establish *claimed run ownership* are the run-local root tuple (`pid`, `argv0`), its `ppid === nodePid` selection rule, and `owned.tree` PPID descendants, all captured after launch; the per-sample socket filters then reuse those PIDs. This is materially stronger than global executable-name scanning, but it is a one-time ancestry snapshot rather than continuous descendant tracking or kernel-authenticated process identity. Do not overstate it as complete process-tree coverage or authenticated session identity. The frozen counter's tests establish predicate coverage over receipt contents, not independent truth of every recorded OS observation.
